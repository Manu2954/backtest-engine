ID: CRIT-001
Component: State Machine
File: backend/app/engine/state_machine.py
Lines: 335-358
Title: Slippage Model Fundamentally Unrealistic
Description:
    Fixed percentage slippage ignores order size vs available liquidity.
    Real slippage depends on: order size / daily volume, market volatility,
    time of day, and asset liquidity class.
Impact:
    - Small orders: Slippage overestimated
    - Large orders: Slippage underestimated by 20-60x
    - Example: $1M order into illiquid market shows 0.05% slippage,
      reality is 2-3% (market impact)
Real-World Failure:
    Strategy shows profitable in backtest, loses money live due to
    execution costs eating all alpha on position entry/exit.
Suggested Fix:
    Implement volatility-adjusted slippage: slippage ∝ ATR × (position_size / avg_volume)
    Or at minimum: Add volume validation and warn when position > 20% daily volume

ID: CRIT-002
Component: State Machine
File: backend/app/engine/state_machine.py
Lines: 625-629, 661-698
Title: Liquidation Logic Incomplete for Leveraged Positions
Description:
    - Liquidation price set once at entry, never recalculated
    - No funding rate charges (perpetual futures charge every 8h)
    - No partial liquidations (real exchanges liquidate in tranches)
    - No maintenance margin vs initial margin distinction
Impact:
    - Positions liquidate at different prices than backtest predicts
    - Funding rates can drain 0.9%+ over 3 days, shifting liquidation threshold
    - Backtest shows profitable leveraged trade; reality: liquidated due to funding
Real-World Failure:
    10x BTC futures position survives in backtest but liquidates live because
    funding rate charges reduced effective margin by $900 on $10K position.
Suggested Fix:
    - Add funding_rate_pct parameter for perpetuals
    - Recalculate liquidation price each bar based on cumulative funding
    - Model partial liquidations (reduce 25% at a time)

Component: State Machine

ID: CRIT-004
Component: Condition Engine
File: backend/app/engine/condition_engine.py
Lines: 23-69, 133
Title: LOOKBACK Operand Allows Positive Offsets (Lookahead Bias)
Status: ✅ FIXED (2026-07-08)
Description:
    The LOOKBACK operand type supported positive offsets like "close:+5" which
    shifts data forward, accessing FUTURE prices. This creates lookahead bias
    that invalidates backtest results.
Fix Applied:
    - Added validation in _parse_lookback() to reject offset > 0
    - Updated docstrings to remove misleading positive offset examples
    - Updated demo_lookback.py to clarify only negative offsets allowed
    - Added unit test test_lookback_positive_offset_rejected()
Impact:
    - Strategy using "close:+5" compares today's price to price 5 bars in future
    - Backtest shows 100% win rate; impossible to replicate live
    - Subtle: User may not realize "+5" means future data
Real-World Failure:
    Strategy condition "close > close:+5" (price will drop) is literally
    using a crystal ball. Backtest perfect, live performance random.
Suggested Fix:
    Add validation in _parse_lookback():
    if offset > 0:
        raise ValueError("LOOKBACK offset must be <= 0 (past data only)")

ID: CRIT-005

Title: MACD Column Extraction Order Wrong (Signal ↔ Histogram Swapped)
Description:

    df_out[f"{alias}_macd"] = macd_df["MACD_12_26_9"]
    df_out[f"{alias}_hist"] = macd_df["MACDh_12_26_9"]
    df_out[f"{alias}_signal"] = macd_df["MACDs_12_26_9"]

ID: CRIT-007
Component: Report Generator
File: backend/app/engine/report_generator.py
Lines: 266-272
Title: Sharpe Ratio Uses Wrong Denominator
Description:
    Code uses daily_returns.std() instead of excess_returns.std()
    The Sharpe ratio should divide excess return mean by excess return std.
Impact:
    - Systematic underestimation of Sharpe when risk_free_rate > 0
    - Strategy ranking affected when comparing across different risk-free assumptions
    - Off by ~0.83% absolute in final Sharpe for typical strategies
Real-World Failure:
    Strategy A (Sharpe 1.5) vs Strategy B (Sharpe 1.4) - choose A.
    With correct calculation: A=1.4, B=1.5 - should have chosen B.
Suggested Fix:
    Line 270 change:
    sharpe = (excess_returns.mean() / excess_returns.std()) * (252 ** 0.5)

ID: CRIT-008
Component: Report Generator
File: backend/app/engine/report_generator.py
Lines: 294-296
Title: Profit Factor Returns 0.0 for Perfect Strategies
Description:
    When gross_loss = 0 (no losing trades), profit_factor returns 0.0
    Should return 999999.0 (or infinity) to indicate perfect strategy.
Impact:
    - Perfect strategy (all wins) shows PF = 0.0
    - Indistinguishable from strategy with no trades
    - User sees "bad" metric for their best strategy
Real-World Failure:
    Strategy A: 10 wins, 5 losses → PF = 2.0
    Strategy B: 10 wins, 0 losses → PF = 0.0 (WRONG)
    User chooses A over B based on this broken metric.
Suggested Fix:
    if gross_loss > 0:
        profit_factor = gross_profit / gross_loss
    elif gross_profit > 0:
        profit_factor = 999999.0
    else:
        profit_factor = 0.0

ID: CT-002
Component: State Machine (Counter-Trade)
File: backend/app/engine/state_machine.py
Lines: 1235-1246, 1269-1280
Title: Counter-Trade Chains Can Spiral Infinitely
Status: ✅ CONFIRMED via test
Description:
    When a counter-trade position exits with a loss via signal, it triggers
    ANOTHER counter-trade. In a bad market, this creates infinite losing chains.
Example:
    LONG -10% loss → SHORT counter
    SHORT -5% loss → LONG counter
    LONG -8% loss → SHORT counter
    ... (continues until account depleted)
Impact:
    HIGH - Can generate unlimited losing trades, draining the account.
Suggested Fix:
    Add is_counter_trade flag to position/trade. Block counter-trades from
    spawning more counter-trades. Or add max_counter_trade_chain parameter.

--------------------------------------------------------------------------------

ID: CT-003
Component: State Machine (Counter-Trade)
File: backend/app/engine/state_machine.py
Lines: 1114-1118, 1146-1150 vs 1346
Title: dynamic_tp_pct_column Overwrites Counter-Trade TP
Status: ✅ CONFIRMED via test
Description:
    Counter-trade sets dynamic_tp_pct = loss% × multiplier at line 1346.
    But during entry fill, if dynamic_tp_pct_column exists, it OVERWRITES
    this value at lines 1114-1118.
Example:
    - LONG loses 10%, counter-trade TP should be 15% (10% × 1.5)
    - But dynamic_tp_pct_column has value 5%
    - Counter-trade exits at 5% instead of 15%
Impact:
    Counter-trade TP is silently replaced, defeating the purpose of the feature.
Suggested Fix:
    Check if pos.dynamic_tp_pct was already set (by counter-trade) before
    overwriting with column value. Counter-trade TP should take priority.
