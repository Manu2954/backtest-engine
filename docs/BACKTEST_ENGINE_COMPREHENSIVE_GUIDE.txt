1.1 WHAT IS THE BACKTEST ENGINE?
--------------------------------

The BacktestEngine is a full-stack application for evaluating technical
indicator-based trading strategies using historical market data. It allows
traders and quantitative analysts to:

  - Define trading strategies using technical indicators
  - Test strategies against historical data
  - Analyze performance metrics
  - Compare strategies against buy-and-hold benchmarks
  - Simulate realistic trading conditions (commissions, slippage, position sizing)

The system supports both stocks (via Yahoo Finance) and cryptocurrencies
(via Binance), making it versatile for different asset classes.


1.2 CORE CONCEPTS
-----------------

A. STRATEGY
   A strategy is a complete trading plan consisting of:
   - Technical indicators (e.g., RSI, MACD, EMA)
   - Entry conditions (when to buy)
   - Exit conditions (when to sell)

B. INDICATORS
   Mathematical calculations applied to price/volume data to identify
   trading opportunities. Each indicator has:
   - Type: RSI, SMA, EMA, MACD, Bollinger Bands, ATR, Stochastic, ADX,
           Ichimoku Cloud, ROC, OBV
   - Alias: A unique name for referencing in conditions (e.g., "rsi_14")
   - Parameters: Settings like period, source column, etc.

C. CONDITIONS
   Rules that determine when to enter or exit trades. Each condition has:
   - Left operand: The value being compared (indicator, OHLCV, scalar, lookback)
   - Operator: How to compare (GT, LT, CROSSES_ABOVE, IS_RISING, etc.)
   - Right operand: What to compare against

D. CONDITION GROUPS
   Collections of conditions combined with AND/OR logic.
   Groups can be further combined using boolean expressions (&&, ||, !) for
   complex logic like: (oversold && trending) || breakout

E. TRADE ATTRIBUTION (Phase 1A)
   Analysis system that tracks which conditions trigger trades and measures
   signal strength to distinguish skill from luck. For each trade:
   - Captures which conditions were met at entry/exit
   - Calculates signal strength (0.0-1.0) based on confluence
   - Measures market return during trade (buy-and-hold baseline)
   - Computes alpha (trade return - market return)
   - Records indicator snapshots at entry/exit points

F. EMPIRICAL BINNING (Phase 1B)
   Data-driven validation that shows which indicator ranges correlate with
   profitable trades. After 50+ trades:
   - Bins each indicator's values into quintiles
   - Calculates average P&L per bin
   - Computes Spearman correlation (indicator value vs P&L)
   - Identifies statistically significant predictors

G. ROBUSTNESS ANALYSIS (Phase 2A)
   Parameter sensitivity testing to identify fragile vs robust strategies:
   - Varies each indicator parameter by ±20% (configurable)
   - Runs baseline + variant backtests in parallel
   - Calculates stability score using Coefficient of Variation
   - Classifies as ROBUST (≥0.8), MODERATE (0.6-0.8), or FRAGILE (<0.6)
   - Generates risk flags and deployment recommendations

H. BACKTEST RUN
   A single test of a strategy against historical data for a specific:
   - Ticker symbol
   - Date range
   - Initial capital
   - Position sizing rules
   - Risk management settings
   - Attribution settings (optional)


1.3 CREATING A TRADING STRATEGY
-------------------------------

A strategy is created by defining indicators and entry/exit conditions.

STEP 1: DEFINE INDICATORS
-------------------------
Each indicator requires:
  - indicator_type: The type of indicator
  - alias: A unique identifier
  - params: Indicator-specific parameters

Example indicators:

  RSI (Relative Strength Index):
    {
      "indicator_type": "RSI",
      "alias": "rsi_14",
      "params": {"period": 14, "source": "close"}
    }

  EMA (Exponential Moving Average):
    {
      "indicator_type": "EMA",
      "alias": "ema_20",
      "params": {"period": 20, "source": "close"}
    }

  MACD (Moving Average Convergence Divergence):
    {
      "indicator_type": "MACD",
      "alias": "macd_12_26_9",
      "params": {"fast": 12, "slow": 26, "signal": 9}
    }
    Note: Creates three columns: macd_12_26_9_macd, macd_12_26_9_signal,
          macd_12_26_9_hist

  Bollinger Bands:
    {
      "indicator_type": "BB",
      "alias": "bb_20",
      "params": {"period": 20, "std_dev": 2.0}
    }
    Note: Creates three columns: bb_20_upper, bb_20_mid, bb_20_lower

  ATR (Average True Range):
    {
      "indicator_type": "ATR",
      "alias": "atr_14",
      "params": {"period": 14}
    }

  ADX (Average Directional Index):
    {
      "indicator_type": "ADX",
      "alias": "adx_14",
      "params": {"period": 14}
    }
    Note: Creates three columns: adx_14, adx_14_dmp (+DI), adx_14_dmn (-DI)

  Ichimoku Cloud:
    {
      "indicator_type": "ICHIMOKU",
      "alias": "ichi",
      "params": {"tenkan": 9, "kijun": 26, "senkou": 52}
    }
    Note: Creates five columns: ichi_tenkan, ichi_kijun, ichi_span_a,
          ichi_span_b, ichi_chikou


STEP 2: DEFINE ENTRY CONDITIONS
-------------------------------
Entry conditions determine when to open a position. They consist of:

OPERAND TYPES:
  - INDICATOR: Reference to a computed indicator (e.g., "rsi_14")
  - OHLCV: Price data columns ("open", "high", "low", "close", "volume")
  - SCALAR: Constant numeric value (e.g., "30", "50.5")
  - LOOKBACK: Historical value ("column:-N" for N bars ago)

OPERATORS:
  - GT:            Greater than
  - LT:            Less than
  - EQ:            Equal to
  - GTE:           Greater than or equal
  - LTE:           Less than or equal
  - CROSSES_ABOVE: Left crosses above right (requires two series)
  - CROSSES_BELOW: Left crosses below right (requires two series)
  - IS_RISING:     Current value > previous value (single series)
  - IS_FALLING:    Current value < previous value (single series)

Example Entry Condition (RSI below 30):
  {
    "logic": "AND",
    "conditions": [
      {
        "left_operand_type": "INDICATOR",
        "left_operand_value": "rsi_14",
        "operator": "LT",
        "right_operand_type": "SCALAR",
        "right_operand_value": "30"
      }
    ]
  }

Example Entry Condition (Price crosses above EMA):
  {
    "logic": "AND",
    "conditions": [
      {
        "left_operand_type": "OHLCV",
        "left_operand_value": "close",
        "operator": "CROSSES_ABOVE",
        "right_operand_type": "INDICATOR",
        "right_operand_value": "ema_20"
      }
    ]
  }

Example Entry Condition with LOOKBACK (ADX rising over 3 bars):
  {
    "logic": "AND",
    "conditions": [
      {
        "left_operand_type": "INDICATOR",
        "left_operand_value": "adx_14",
        "operator": "GT",
        "right_operand_type": "LOOKBACK",
        "right_operand_value": "adx_14:-3"
      }
    ]
  }


STEP 3: DEFINE EXIT CONDITIONS
------------------------------
Exit conditions determine when to close a position. They use the same
format as entry conditions but are evaluated while in a position.


STEP 4: COMBINE WITH EXPRESSIONS (ADVANCED)
-------------------------------------------
For complex strategies, you can define multiple named condition groups
and combine them with boolean expressions.

Example Expression-Based Strategy:
  Entry Groups:
    "oversold": RSI < 30
    "trending": ADX > 25
    "bullish_cross": MACD crosses above signal

  Entry Expression: "(oversold && trending) || bullish_cross"

This enters when EITHER:
  - RSI is below 30 AND ADX is above 25
  - OR MACD crosses above its signal line

Supported Expression Operators:
  - && or & : AND
  - || or | : OR
  - ! or ~  : NOT
  - ()      : Grouping


1.4 RUNNING A BACKTEST
----------------------

A backtest is executed by providing:

REQUIRED PARAMETERS:
  - strategy_id:      UUID of the strategy to test
  - ticker:           Symbol to trade (e.g., "AAPL", "BTCUSDT")
  - asset_class:      "STOCK" or "CRYPTO"
  - start_date:       Start of test period
  - end_date:         End of test period
  - initial_capital:  Starting capital amount

OPTIONAL PARAMETERS:

  Bar Resolution (bar_resolution):
    - "1m", "5m", "15m", "30m", "1h" (intraday)
    - "1d" (daily - default)
    - "1wk" (weekly)
    - "1mo" (monthly)

  Position Sizing (position_size_type, position_size_value):
    - "full_capital": Use all available cash (default)
    - "percent_capital": Use X% of total capital (value = percentage)
    - "fixed_amount": Use fixed dollar amount per trade (value = dollars)
    - "risk_based": Size based on risk percentage and stop distance
                    (value = risk % of equity to risk per trade)

      Risk-based sizing calculates position size as:
      Position Size = (Equity × Risk%) / Stop Distance%

      Example: $10,000 equity, 2% risk, 5% stop loss
      → Position Size = ($10,000 × 0.02) / 0.05 = $4,000

  Risk Management:
    - stop_loss_pct:    Exit if price drops X% from entry
    - take_profit_pct:  Exit if price rises X% from entry
    - dynamic_stop_loss: Indicator-based trailing stop (e.g., ATR-based)

  Transaction Costs:
    - commission_per_trade: Fixed cost per trade (e.g., $5)
    - commission_pct:       Percentage of trade value (e.g., 0.1%)
    - slippage_pct:         Price slippage on execution (e.g., 0.05%)

  Periodic Contributions:
    - amount:       Dollar amount to add
    - frequency:    "daily", "weekly", "monthly", "interval_days"
    - interval_days: Custom interval (if frequency = "interval_days")
    - include_start: Whether to contribute on first bar

  Attribution Analysis (enable_attribution):
    - true (default): Capture trade attribution data
    - false:          Skip attribution (slightly faster)

    When enabled, each trade captures:
    - Which conditions triggered entry/exit
    - Signal strength (0.0-1.0)
    - Market return during trade
    - Alpha (trade return - market return)
    - Indicator snapshots at entry/exit


1.5 UNDERSTANDING RESULTS
-------------------------

A completed backtest produces a comprehensive report:

PERFORMANCE METRICS:
  - total_return_pct:       Total percentage return
  - cagr:                   Compound Annual Growth Rate
  - sharpe_ratio:           Risk-adjusted return (annualized)
  - max_drawdown_pct:       Maximum peak-to-trough decline
  - longest_drawdown_days:  Longest time in drawdown

TRADE STATISTICS:
  - total_trades:           Number of completed trades
  - win_rate:               Percentage of profitable trades
  - avg_win:                Average profit on winning trades
  - avg_loss:               Average loss on losing trades
  - avg_win_loss:           Ratio of avg win to avg loss
  - profit_factor:          Gross profit / gross loss
  - largest_win:            Biggest single winning trade
  - largest_loss:           Biggest single losing trade
  - avg_trade_duration_days: Average time in a trade

FINAL VALUES:
  - final_capital:          Ending portfolio value

BENCHMARK COMPARISON:
  - benchmark_return_pct:      Buy-and-hold return
  - benchmark_final_capital:   Buy-and-hold ending value
  - benchmark_sharpe_ratio:    Buy-and-hold Sharpe ratio
  - benchmark_max_drawdown_pct: Buy-and-hold max drawdown
  - alpha:                     Strategy return - benchmark return
  - beta:                      Correlation with benchmark

TRADE LOG:
Each trade records:
  - entry_date, entry_price
  - exit_date, exit_price
  - shares traded
  - pnl (profit/loss in dollars)
  - pnl_pct (profit/loss percentage)
  - trade_duration_days
  - exit_reason: "signal", "stop_loss", "take_profit", "trailing_stop",
                 "force_close"

  Attribution fields (if enabled):
  - entry_conditions_met: List of condition UUIDs that triggered entry
  - exit_conditions_met: List of condition UUIDs that triggered exit
  - entry_signal_strength: Signal strength at entry (0.0-1.0)
  - market_return_during_trade: Buy-and-hold return for same period
  - alpha: Trade return - market return (skill vs luck)
  - indicator_snapshot_entry: All indicator values at entry
  - indicator_snapshot_exit: All indicator values at exit

ATTRIBUTION REPORT (Phase 1A):
Strategy-level insights when attribution is enabled:
  - total_alpha: Sum of alpha across all trades
  - alpha_percentage: What % of returns came from skill vs market
  - signal_strength breakdown:
    * Strong signals (>0.7): Count, win rate, avg alpha
    * Medium signals (0.3-0.7): Count, win rate, avg alpha
    * Weak signals (<0.3): Count, win rate, avg alpha
  - condition_frequency: How often each condition triggered

  Key Insight: Are your strong signals actually better performers?

BINNING ANALYSIS (Phase 1B):
Indicator validation report (requires 50+ trades):
  For each indicator used in entry conditions:
  - Quintile bins showing:
    * Value range (e.g., RSI 10-30)
    * Trade count in that range
    * Average P&L in that range
    * Win rate in that range
  - Spearman correlation (indicator value vs P&L)
  - Statistical significance (p-value)
  - Summary identifying strongest predictors

  Example: "RSI has -0.72 correlation (p<0.001) - lower RSI = higher profits"

  Key Insight: Which indicator ranges actually correlate with profitable trades?


1.6 SUPPORTED FEATURES
----------------------

A. ASSET CLASSES
   - STOCK: Equities (via Yahoo Finance)
   - CRYPTO: Cryptocurrencies (via Binance)

B. DATA PROVIDERS
   - YFinance: Stocks, ETFs, indices, and crypto (BTC-USD format)
     * Free tier, rate limited
     * Intraday data limited to 60 days for stocks
     * Adjusted for splits/dividends

   - Binance: Cryptocurrency pairs (BTCUSDT format)
     * Direct exchange data feed
     * Full historical depth
     * Multiple resolution support
     * IST timezone support

   Provider is automatically selected based on asset_class parameter.

C. TIME RESOLUTIONS
   Stocks: 1m, 2m, 5m, 15m, 30m, 60m, 90m, 1h, 1d, 5d, 1wk, 1mo, 3mo
   Crypto: 1m, 3m, 5m, 15m, 30m, 1h, 2h, 4h, 6h, 8h, 12h, 1d, 3d, 1w, 1mo

D. TECHNICAL INDICATORS
   - RSI (Relative Strength Index)
   - SMA (Simple Moving Average)
   - EMA (Exponential Moving Average)
   - MACD (Moving Average Convergence Divergence)
   - Bollinger Bands
   - ATR (Average True Range)
   - Stochastic Oscillator
   - ADX (Average Directional Index)
   - Ichimoku Cloud
   - ROC (Rate of Change)
   - OBV (On-Balance Volume)

E. POSITION SIZING METHODS
   - Full capital: Invests entire available cash balance
   - Percentage of capital: Fixed % of total equity (e.g., 10%)
   - Fixed dollar amount: Same dollar amount per trade
   - Risk-based: Size based on risk % and stop distance
                 Position Size = (Equity × Risk%) / Stop Distance%

F. RISK MANAGEMENT
   - Fixed stop loss (percentage from entry price)
   - Fixed take profit (percentage from entry price)
   - Dynamic trailing stop (indicator-based, e.g., ATR trailing)

G. TRANSACTION COSTS
   - Fixed commission per trade (e.g., $5)
   - Percentage commission (e.g., 0.1% of trade value)
   - Slippage simulation (percentage price impact)

H. PERIODIC CONTRIBUTIONS
   - Daily, weekly, monthly, or custom interval
   - Dollar-cost averaging simulation

I. ADVANCED LOGIC FEATURES
   - LOOKBACK operand: Compare current vs historical values
     Example: "rsi_14 > rsi_14:-5" (RSI higher than 5 bars ago)

   - Boolean expressions: Combine condition groups with &&, ||, !
     Example: "(oversold && trending) || breakout"

   - Crossover detection: CROSSES_ABOVE, CROSSES_BELOW operators
   - Trend detection: IS_RISING, IS_FALLING operators

J. ATTRIBUTION & VALIDATION (Phase 1A/1B)
   - Trade-level attribution: Track which conditions drive profitability
   - Signal strength scoring: Measure confluence (0.0-1.0)
   - Alpha calculation: Separate skill from market movement
   - Empirical binning: Validate indicator effectiveness with statistics
   - Correlation analysis: Spearman correlation per indicator
   - Significance testing: Identify statistically valid predictors

K. ROBUSTNESS ANALYSIS (Phase 2A)
   - Parameter sensitivity testing: Vary params by ±20%
   - Stability scoring: Coefficient of Variation across variants
   - Robustness classification: ROBUST / MODERATE / FRAGILE
   - Risk flag generation: Specific warnings about fragility
   - Parallel execution: Variant backtests run concurrently via Celery
   - Actionable recommendations: Deploy / caution / do not deploy

2.2 DATA FLOW PIPELINE
----------------------

When a backtest is executed, data flows through these stages:

STAGE 1: DATA FETCHING (data_layer.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. Check Redis cache for exact date range match                       │
│     └─ Hit? Return cached DataFrame                                    │
│                                                                        │
│  2. Check PostgreSQL for stored OHLCV bars                             │
│     └─ Covers range with sufficient bars? Return + cache               │
│                                                                        │
│  3. Fetch from external provider (yfinance/binance)                    │
│     └─ Normalize to standard format                                    │
│     └─ Store in PostgreSQL                                             │
│     └─ Cache in Redis                                                  │
│     └─ Return DataFrame                                                │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

STAGE 2: INDICATOR COMPUTATION (indicator_layer.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. Validate OHLCV columns present                                     │
│                                                                        │
│  2. For each indicator definition:                                     │
│     └─ Dispatch to pandas-ta function based on type                    │
│     └─ Handle multi-column outputs (MACD, BB, etc.)                    │
│     └─ Append to DataFrame with alias names                            │
│                                                                        │
│  3. Track indicator columns in DataFrame metadata                      │
│                                                                        │
│  4. Determine warmup period (first bar where all indicators valid)     │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

STAGE 3: WARMUP TRIMMING (indicator_layer.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. Find first bar where ALL indicator columns have valid values       │
│     (not NaN)                                                          │
│                                                                        │
│  2. Trim DataFrame to remove warmup period                             │
│                                                                        │
│  3. Validate sufficient bars remain (minimum 30)                       │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

STAGE 4: CONDITION EVALUATION (condition_engine.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. For each condition in a group:                                     │
│     └─ Resolve left operand to Series/scalar (INDICATOR/OHLCV/SCALAR) │
│     └─ Resolve right operand to Series/scalar (or LOOKBACK)           │
│     └─ Apply operator (GT/LT/CROSSES_ABOVE/IS_RISING) → Boolean Series│
│                                                                        │
│  2. Combine conditions with group logic (AND/OR)                       │
│                                                                        │
│  3. If using boolean expressions:                                      │
│     └─ Evaluate each named group independently                         │
│     └─ Build namespace mapping group names to boolean results          │
│     └─ Execute boolean expression (&&, ||, !, parentheses)             │
│     └─ Return final boolean signal                                     │
│                                                                        │
│  4. If attribution enabled:                                            │
│     └─ Track which conditions evaluated to True                        │
│     └─ Calculate signal strength (confluence-based: 0.0-1.0)           │
│     └─ Capture indicator snapshot at signal bar                        │
│     └─ Return (signal, attribution_data) tuple                         │
│                                                                        │
│  Output: entry_signal (Boolean Series), exit_signal (Boolean Series)   │
│          + attribution_data (if enabled)                               │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

STAGE 5: BACKTEST SIMULATION (state_machine.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  STATE MACHINE:                                                        │
│    NO_POSITION ──entry_signal──▶ PENDING_ENTRY                         │
│    PENDING_ENTRY ──next bar──▶ IN_POSITION (fill at open)              │
│    IN_POSITION ──exit_signal/stop/profit──▶ PENDING_EXIT               │
│    PENDING_EXIT ──next bar──▶ NO_POSITION (fill at open)               │
│                                                                        │
│  For each bar:                                                         │
│    1. Apply periodic contributions (if configured)                     │
│    2. Fill pending entry at bar open (with slippage/commission)        │
│       └─ If attribution enabled: capture entry attribution data        │
│    3. Fill pending exit at bar open (with slippage/commission)         │
│       └─ If attribution enabled: capture exit attribution data         │
│    4. Check risk management (stop loss, take profit, dynamic stop)     │
│    5. Calculate mark-to-market equity at bar close                     │
│    6. Evaluate signals for next bar (with attribution if enabled)      │
│       └─ Capture which conditions triggered, signal strength           │
│    7. Update equity curve                                              │
│                                                                        │
│  At end:                                                               │
│    - Handle pending entries on last bar                                │
│    - Force close any open positions                                    │
│    - Calculate trade-level attribution (if enabled):                   │
│      * Market return during trade (buy-and-hold baseline)              │
│      * Alpha (trade return - market return)                            │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

STAGE 7: PERSISTENCE (via SQLAlchemy async)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. Create BacktestRun record with results                             │
│     └─ Store report as JSONB                                           │
│     └─ Store equity curve as JSONB                                     │
│     └─ Store enable_attribution flag                                   │
│                                                                        │
│  2. Create TradeLog records for each completed trade                   │
│     └─ Standard fields: entry/exit dates, prices, P&L, duration        │
│     └─ Attribution fields (if enabled): conditions_met, signal_strength│
│        alpha, indicator_snapshots                                      │

D. STATE MACHINE (app/engine/state_machine.py)
----------------------------------------------
Purpose: Simulate trade execution with realistic fills

Main Function:
  run_backtest(df, entry_signal, exit_signal, initial_capital, enable_attribution=True, ...)
    - Returns (trade_log, equity_curve)
    - Now supports attribution tracking when enabled

Key Parameters:
  - asset_class: "STOCK" (whole shares) or "CRYPTO" (fractional)
  - position_size_type/value: How to size positions
  - stop_loss_pct, take_profit_pct: Risk management
  - dynamic_stop_column: Indicator-based trailing stop
  - commission_per_trade, commission_pct: Transaction costs
  - slippage_pct: Price slippage simulation
  - periodic_contribution: Regular cash additions
  - enable_attribution: Enable trade attribution tracking (default: True)

State Machine Logic:
  1. NO_POSITION: Check for entry signal
     → If True, set pending_entry = True
     → If attribution enabled: capture entry conditions met

  2. PENDING_ENTRY: At next bar open
     → Calculate position size
     → Apply slippage to price
     → Deduct cost + commission from cash
     → Record entry_date, entry_price, shares
     → If attribution enabled: capture entry attribution data

  3. IN_POSITION: Check for exit conditions
     a. Strategy exit signal
     b. Stop loss triggered (price dropped X%)
     c. Take profit triggered (price gained X%)
     d. Dynamic stop triggered (price < indicator value)
     → Set pending_exit = True
     → If attribution enabled: capture exit conditions met

  4. PENDING_EXIT: At next bar open
     → Apply slippage to exit price
     → Deduct commission
     → Add proceeds to cash
     → Record trade in trade_log
     → If attribution enabled: calculate market return, alpha

Position Sizing Logic:
  - full_capital: shares = cash / price
  - percent_capital: shares = (total_capital * pct / 100) / price
  - fixed_amount: shares = fixed_dollars / price
  - risk_based: shares = (equity * risk_pct) / (entry - stop)

Commission Handling:
  - Fixed: commission_per_trade
  - Percentage: commission_pct / 100 * (shares * price)
  - Total: fixed + percentage
  - Applied on both entry and exit

Slippage Handling:
  - Entry: execution_price = open * (1 + slippage_pct / 100)
  - Exit: execution_price = open * (1 - slippage_pct / 100)

TradeRecord Structure:
  @dataclass
  class TradeRecord:
      entry_date: pd.Timestamp
      entry_price: float
      exit_date: pd.Timestamp
      exit_price: float
      shares: float
      pnl: float
      pnl_pct: float
      trade_duration_days: int
      exit_reason: str
      total_commission: float

      # Attribution fields (Phase 1A - optional)
      entry_conditions_met: list[str] | None
      exit_conditions_met: list[str] | None
      entry_signal_strength: float | None
      market_return_during_trade: float | None
      alpha: float | None
      indicator_snapshot_entry: dict | None
      indicator_snapshot_exit: dict | None
      pnl: float              # (exit - entry) * shares - commissions
      pnl_pct: float          # pnl / cost * 100
      trade_duration_days: int
      exit_reason: str        # signal, stop_loss, take_profit, etc.
      entry_commission: float
      exit_commission: float
      total_commission: float


E. REPORT GENERATOR (app/engine/report_generator.py)
----------------------------------------------------
Purpose: Calculate comprehensive performance metrics

Main Function:
  generate_report(trade_log, equity_curve, initial_capital, benchmark_equity,
                  enable_attribution=True, indicators=None)
    - Returns dict with all performance metrics
    - Now generates attribution and binning reports when enabled

Supporting Functions:
  calculate_buy_and_hold_equity(df, initial_capital, asset_class)
    - Simulates buy-and-hold strategy
    - Returns benchmark equity curve

  generate_attribution_report(trade_log)
    - NEW (Phase 1A): Generates attribution insights
    - Returns dict with total_alpha, signal strength breakdown, condition frequency

  generate_binning_report(trade_log, indicators)
    - NEW (Phase 1B): Generates empirical binning analysis
    - Requires 50+ trades
    - Returns dict with quintile bins, correlations, significance tests

  _max_drawdown(equity)
    - Calculates maximum peak-to-trough decline
    - Returns percentage as negative number

  _longest_drawdown_days(equity)
    - Finds longest period below previous high
    - Returns days

  _calculate_benchmark_stats(strategy_equity, benchmark_equity, ...)
    - Calculates alpha, beta, benchmark comparison

Metric Calculations:
  - total_return_pct: (final - initial) / initial * 100
  - cagr: (final / initial)^(1/years) - 1
  - sharpe_ratio: (mean_daily_return / std_daily_return) * sqrt(252)
  - calmar_ratio: cagr / abs(max_drawdown)
  - win_rate: len(wins) / total_trades * 100
  - profit_factor: gross_profit / gross_loss
  - alpha: strategy_return - benchmark_return
  - beta: cov(strategy, benchmark) / var(benchmark)

3.2 STRATEGY DEVELOPMENT WORKFLOW
---------------------------------

STEP 1: HYPOTHESIS FORMATION
   - Identify market inefficiency or pattern
   - Define entry/exit logic conceptually
   - Select appropriate indicators

STEP 2: STRATEGY DEFINITION
   - Create strategy via API
   - Define indicator parameters
   - Specify entry/exit conditions
   - Start with simple conditions, add complexity later

STEP 3: INITIAL BACKTEST
   - Run backtest on historical data
   - Use default position sizing (full_capital)
   - No transaction costs initially

STEP 4: RESULTS ANALYSIS
   - Review total return, Sharpe ratio, Calmar ratio, max drawdown
   - Examine trade log for patterns
   - Compare against buy-and-hold benchmark
   - Check win rate and profit factor

   If attribution enabled:
   - Review signal strength breakdown (strong/medium/weak)
   - Analyze condition frequency (which conditions trigger most)
   - Check alpha vs market return (skill vs luck)
   - Examine indicator snapshots at trade entry/exit

   If 50+ trades:
   - Review binning analysis report
   - Identify which indicator ranges correlate with profitable trades
   - Look for statistically significant predictors (p < 0.05)
   - Consider removing indicators with weak correlations

STEP 5: REFINEMENT
   - Adjust indicator parameters based on binning insights
   - Remove conditions with weak predictive power
   - Add/strengthen conditions that show high correlation
   - Try different expression combinations
   - Test across multiple time periods

   Attribution-driven refinement:
   - If weak signals perform as well as strong signals → simplify strategy
   - If specific conditions rarely trigger → consider removing
   - If indicator snapshots show clustering → adjust thresholds

STEP 6: REALISTIC SIMULATION
   - Add transaction costs (commissions, slippage)
   - Test different position sizing methods
   - Add stop loss and take profit
   - Include periodic contributions

STEP 7: ROBUSTNESS TESTING
   - Test on different tickers
   - Test on different time periods
   - Test on different asset classes
   - Check for overfitting

   Attribution validation:
   - Compare attribution reports across different time periods
   - Verify strong signals remain strong in out-of-sample data
   - Check if binning correlations hold on new data
   - Ensure alpha remains positive (skill, not luck)

STEP 8: PARAMETER SENSITIVITY ANALYSIS (Phase 2A)
   - Submit robustness analysis via /robustness/parameter-sensitivity
   - Review stability score and robustness classification
   - Check risk flags for specific concerns
   - Examine per-metric CVs to identify unstable metrics

   Take action based on results:
   - ROBUST: Proceed to deployment with confidence
   - MODERATE: Consider narrower parameter ranges, additional filters,
               or reduced position sizing
   - FRAGILE: Do NOT deploy; simplify strategy or find robust parameters

   Key insight: A strategy that only works with exact parameter values
   is unlikely to work in live trading where conditions shift.

4.1 TRADE ATTRIBUTION SYSTEM (Phase 1A)
---------------------------------------

PURPOSE:
Understand which conditions drive profitability and distinguish skill from luck.

WHAT IT TRACKS:
For each trade:
  - Which conditions triggered entry (condition UUIDs)
  - Which conditions triggered exit (condition UUIDs)
  - Signal strength at entry (0.0-1.0, confluence-based)
  - Market return during trade period (buy-and-hold baseline)
  - Alpha (trade return - market return = skill component)
  - Indicator values at entry time (full snapshot)
  - Indicator values at exit time (full snapshot)

STRATEGY-LEVEL INSIGHTS:
  - Total alpha: Sum of alpha across all trades
  - Alpha percentage: What % of returns came from skill vs market
  - Signal strength breakdown:
    * Strong signals (>0.7): Count, win rate, avg alpha
    * Medium signals (0.3-0.7): Count, win rate, avg alpha
    * Weak signals (<0.3): Count, win rate, avg alpha
  - Condition frequency: How often each condition triggered

KEY QUESTION ANSWERED:
"Are my strong signals actually better performers than weak signals?"

HOW TO USE:
1. Enable attribution in backtest request (enabled by default)
2. After backtest completes, examine report["attribution"]
3. Compare strong vs weak signal performance
4. Identify frequently triggered conditions
5. Review indicator snapshots for patterns

EXAMPLE INSIGHT:
```
Strong signals (>0.7): 25 trades, 72% win rate, +3.5% avg alpha
Weak signals (<0.3): 20 trades, 35% win rate, -0.8% avg alpha

→ Strategy has genuine edge when signals are strong
→ Consider filtering out trades with signal strength < 0.5
```

IMPLEMENTATION DETAILS:
- Pluggable calculator architecture (easy to extend)
- Phase 1A uses ConfluenceStrengthCalculator (conditions_met / total_conditions)
- Minimal performance overhead (<5% when enabled)
- Can be disabled for faster backtests


4.2 EMPIRICAL BINNING ANALYSIS (Phase 1B)
-----------------------------------------

PURPOSE:
Validate which indicator ranges actually correlate with profitable trades using
data-driven statistics instead of arbitrary thresholds.

WHAT IT ANALYZES:
For each indicator used in entry conditions (requires 50+ trades):
  - Divides indicator values into quintiles (5 bins)
  - Calculates average P&L per bin
  - Calculates win rate per bin
  - Computes trade-level Spearman correlation (indicator value vs P&L)
  - Tests statistical significance (p-value)

- **|correlation| > 0.3, p < 0.05**: Moderate predictor, useful but not critical

1. Run backtest with 50+ trades

SMA_50: 0.15 correlation (p=0.35)
→ No statistically significant relationship
→ SMA_50 crossover not adding value
→ Consider removing this condition
```

ADVANTAGES OVER FIXED THRESHOLDS:
- Data-driven: Learns from actual trade outcomes
- Asset-agnostic: Bins adapt to each ticker's characteristics
- Statistical validation: P-values show confidence level
- No arbitrary rules: No hardcoded "RSI 30/70" assumptions

LIMITATIONS:
- Requires 50+ trades (not 20 - more data = better statistics)
- Entry indicators only (exit values are post-hoc)
- Crossover indicators skipped (no single value to bin)
- Single-dimension analysis (no multi-indicator interactions yet)

4.4 PARAMETER SENSITIVITY ANALYSIS (Phase 2A)
---------------------------------------------

PURPOSE:
Identify fragile vs robust strategies by testing how performance changes when
indicator parameters are varied. A robust strategy maintains similar performance
across parameter variations; a fragile strategy's performance swings wildly,
suggesting overfitting to specific parameter values.

THE PROBLEM IT SOLVES:
Traders often "optimize" indicator parameters to maximize backtest returns.
This creates a false sense of confidence - the strategy works great on historical
data with those exact parameters, but fails in live trading when market
conditions shift slightly. Parameter sensitivity analysis exposes this risk.

HOW IT WORKS:
1. Takes your strategy with its indicator parameters (e.g., RSI period=14)
2. Generates variants by varying each numeric parameter by ±variation_pct
   (default ±20%)
   Example: RSI(14) generates RSI(11) and RSI(17)
3. Runs baseline backtest + all variant backtests in parallel via Celery
4. Collects key metrics from each variant (return, Sharpe, win rate, etc.)
5. Calculates stability score using Coefficient of Variation (CV)
6. Classifies strategy robustness level

STABILITY SCORE CALCULATION:
For each metric (total_return_pct, sharpe_ratio, win_rate):
  1. Collect values from baseline + all variants
  2. Calculate Coefficient of Variation: CV = std_dev / |mean|
  3. Average CVs across metrics: mean_CV
  4. Stability Score = max(0, min(1, 1 - mean_CV))

INTERPRETATION:
  - CV close to 0: Metrics are stable across variants
  - CV > 1: Metrics swing more than 100% from the mean
  - Stability Score 1.0: Perfect stability (all variants same)
  - Stability Score 0.0: Extreme instability (huge variation)

ROBUSTNESS CLASSIFICATION:
  - ROBUST (score ≥ 0.8): Metrics vary < 20% across variants
    → Safe to deploy with confidence

  - MODERATE (score 0.6-0.8): Metrics vary 20-40%
    → Use with caution; consider tighter parameter ranges

  - FRAGILE (score < 0.6): Metrics vary > 40%
    → DO NOT DEPLOY; suggests overfitting to specific parameters

```

   RSI(11): +22.1% return (Δ -3.4%)
   RSI(17): +28.2% return (Δ +2.7%)

5. Conclusion: Strategy performs consistently across ±20% parameter

COMPARISON WITH TRADITIONAL OPTIMIZATION:
Traditional "parameter optimization" finds the BEST parameters:
  → RSI(14) gives 25.5% return
  → RSI(12) gives 28.3% return ← "optimal"
  → RSI(16) gives 24.1% return

  User picks RSI(12) because it's "best."

Parameter Sensitivity Analysis asks: "What if I'm wrong?"
  → RSI(12) ±20% = RSI(10) to RSI(14)
  → If RSI(10) gives -5% and RSI(14) gives +25.5%...
  → That's a FRAGILE strategy! The "optimal" parameter is on a knife edge.

The goal is not to find the best parameters, but to find ROBUST parameters
where small errors don't cause large performance swings.

  - generate_risk_flags(baseline_metrics, variant_metrics, metric_cvs)

  - generate_recommendation(robustness_level, risk_flags, stability_score)
    Returns actionable recommendation string

Celery Task: app/tasks/robustness_task.py
  - run_parameter_sensitivity_analysis(strategy_id, backtest_params, variation_pct)
    Orchestrates the full analysis workflow:
    1. Creates RobustnessAnalysis record (status=PENDING)
    2. Loads strategy with indicators and conditions
    3. Runs baseline backtest
    4. Generates parameter variants
    5. Creates temporary strategies for each variant

    11. Updates analysis record (status=COMPLETE)

Database Models: app/models/robustness.py
  - RobustnessAnalysis: Stores analysis config and results
    * id, strategy_id, analysis_type, status
    * params (JSONB): variation_pct, backtest_params
    * report (JSONB): full analysis results
    * created_at, completed_at, error_message

  - RobustnessVariantBacktest: Links variants to backtest runs
    * analysis_id, backtest_run_id
    * variant_label, variant_params (JSONB)

API Routes: app/api/routes/robustness.py

  - Smoke test: scripts/robustness_smoke.py

PERFORMANCE:
  - 2 indicators × 1 param each × 2 directions = 4 variants
  - 4 variant backtests run in parallel via Celery
  - Typical analysis: 1-5 minutes depending on date range and indicators
  - Temporary strategies cleaned up after analysis completes

LIMITATIONS:

  - Zero or negative parameters are skipped
  - Small integers may not produce variants (e.g., period=2 ± 20% rounds to 2)
  - Crossover indicators with no numeric params generate no variants
