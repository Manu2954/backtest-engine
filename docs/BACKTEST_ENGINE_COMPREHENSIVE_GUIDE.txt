1.1 WHAT IS THE BACKTEST ENGINE?
--------------------------------

The BacktestEngine is a full-stack application for evaluating technical
indicator-based trading strategies using historical market data. It allows
traders and quantitative analysts to:

  - Define trading strategies using technical indicators
  - Test strategies against historical data
  - Analyze performance metrics
  - Compare strategies against buy-and-hold benchmarks
  - Simulate realistic trading conditions (commissions, slippage, position sizing)

The system supports both stocks (via Yahoo Finance) and cryptocurrencies
(via Binance), making it versatile for different asset classes.


1.2 CORE CONCEPTS
-----------------

A. STRATEGY
   A strategy is a complete trading plan consisting of:
   - Technical indicators (e.g., RSI, MACD, EMA)
   - Entry conditions (when to buy)
   - Exit conditions (when to sell)

B. INDICATORS
   Mathematical calculations applied to price/volume data to identify
   trading opportunities. Each indicator has:
   - Type: RSI, SMA, EMA, MACD, Bollinger Bands, ATR, Stochastic, ADX,
           Ichimoku Cloud, ROC, OBV
   - Alias: A unique name for referencing in conditions (e.g., "rsi_14")
   - Parameters: Settings like period, source column, etc.

C. CONDITIONS
   Rules that determine when to enter or exit trades. Each condition has:
   - Left operand: The value being compared (indicator, OHLCV, scalar, lookback)
   - Operator: How to compare (GT, LT, CROSSES_ABOVE, IS_RISING, etc.)
   - Right operand: What to compare against

D. CONDITION GROUPS
   Collections of conditions combined with AND/OR logic.
   Groups can be further combined using boolean expressions (&&, ||, !) for
   complex logic like: (oversold && trending) || breakout

E. TRADE ATTRIBUTION (Phase 1A)
   Analysis system that tracks which conditions trigger trades and measures
   signal strength to distinguish skill from luck. For each trade:
   - Captures which conditions were met at entry/exit
   - Calculates signal strength (0.0-1.0) based on confluence
   - Measures market return during trade (buy-and-hold baseline)
   - Computes alpha (trade return - market return)
   - Records indicator snapshots at entry/exit points

F. EMPIRICAL BINNING (Phase 1B)
   Data-driven validation that shows which indicator ranges correlate with
   profitable trades. After 50+ trades:
   - Bins each indicator's values into quintiles
   - Calculates average P&L per bin
   - Computes Spearman correlation (indicator value vs P&L)
   - Identifies statistically significant predictors

G. ROBUSTNESS ANALYSIS (Phase 2A)
   Parameter sensitivity testing to identify fragile vs robust strategies:
   - Varies each indicator parameter by ±20% (configurable)
   - Runs baseline + variant backtests in parallel
   - Calculates stability score using Coefficient of Variation
   - Classifies as ROBUST (≥0.8), MODERATE (0.6-0.8), or FRAGILE (<0.6)
   - Generates risk flags and deployment recommendations

H. BACKTEST RUN
   A single test of a strategy against historical data for a specific:
   - Ticker symbol
   - Date range
   - Initial capital
   - Position sizing rules
   - Risk management settings
   - Attribution settings (optional)


1.3 CREATING A TRADING STRATEGY
-------------------------------

A strategy is created by defining indicators and entry/exit conditions.

STEP 1: DEFINE INDICATORS
-------------------------
Each indicator requires:
  - indicator_type: The type of indicator
  - alias: A unique identifier
  - params: Indicator-specific parameters

Example indicators:

  RSI (Relative Strength Index):
    {
      "indicator_type": "RSI",
      "alias": "rsi_14",
      "params": {"period": 14, "source": "close"}
    }

  EMA (Exponential Moving Average):
    {
      "indicator_type": "EMA",
      "alias": "ema_20",
      "params": {"period": 20, "source": "close"}
    }

  MACD (Moving Average Convergence Divergence):
    {
      "indicator_type": "MACD",
      "alias": "macd_12_26_9",
      "params": {"fast": 12, "slow": 26, "signal": 9}
    }
    Note: Creates three columns: macd_12_26_9_macd, macd_12_26_9_signal,
          macd_12_26_9_hist

  Bollinger Bands:
    {
      "indicator_type": "BB",
      "alias": "bb_20",
      "params": {"period": 20, "std_dev": 2.0}
    }
    Note: Creates three columns: bb_20_upper, bb_20_mid, bb_20_lower

  ATR (Average True Range):
    {
      "indicator_type": "ATR",
      "alias": "atr_14",
      "params": {"period": 14}
    }

  ADX (Average Directional Index):
    {
      "indicator_type": "ADX",
      "alias": "adx_14",
      "params": {"period": 14}
    }
    Note: Creates three columns: adx_14, adx_14_dmp (+DI), adx_14_dmn (-DI)

  Ichimoku Cloud:
    {
      "indicator_type": "ICHIMOKU",
      "alias": "ichi",
      "params": {"tenkan": 9, "kijun": 26, "senkou": 52}
    }
    Note: Creates five columns: ichi_tenkan, ichi_kijun, ichi_span_a,
          ichi_span_b, ichi_chikou


STEP 2: DEFINE ENTRY CONDITIONS
-------------------------------
Entry conditions determine when to open a position. They consist of:

OPERAND TYPES:
  - INDICATOR: Reference to a computed indicator (e.g., "rsi_14")
  - OHLCV: Price data columns ("open", "high", "low", "close", "volume")
  - SCALAR: Constant numeric value (e.g., "30", "50.5")
  - LOOKBACK: Historical value ("column:-N" for N bars ago)

OPERATORS:
  - GT:            Greater than
  - LT:            Less than
  - EQ:            Equal to
  - GTE:           Greater than or equal
  - LTE:           Less than or equal
  - CROSSES_ABOVE: Left crosses above right (requires two series)
  - CROSSES_BELOW: Left crosses below right (requires two series)
  - IS_RISING:     Current value > previous value (single series)
  - IS_FALLING:    Current value < previous value (single series)

Example Entry Condition (RSI below 30):
  {
    "logic": "AND",
    "conditions": [
      {
        "left_operand_type": "INDICATOR",
        "left_operand_value": "rsi_14",
        "operator": "LT",
        "right_operand_type": "SCALAR",
        "right_operand_value": "30"
      }
    ]
  }

Example Entry Condition (Price crosses above EMA):
  {
    "logic": "AND",
    "conditions": [
      {
        "left_operand_type": "OHLCV",
        "left_operand_value": "close",
        "operator": "CROSSES_ABOVE",
        "right_operand_type": "INDICATOR",
        "right_operand_value": "ema_20"
      }
    ]
  }

Example Entry Condition with LOOKBACK (ADX rising over 3 bars):
  {
    "logic": "AND",
    "conditions": [
      {
        "left_operand_type": "INDICATOR",
        "left_operand_value": "adx_14",
        "operator": "GT",
        "right_operand_type": "LOOKBACK",
        "right_operand_value": "adx_14:-3"
      }
    ]
  }


STEP 3: DEFINE EXIT CONDITIONS
------------------------------
Exit conditions determine when to close a position. They use the same
format as entry conditions but are evaluated while in a position.


STEP 4: COMBINE WITH EXPRESSIONS (ADVANCED)
-------------------------------------------
For complex strategies, you can define multiple named condition groups
and combine them with boolean expressions.

Example Expression-Based Strategy:
  Entry Groups:
    "oversold": RSI < 30
    "trending": ADX > 25
    "bullish_cross": MACD crosses above signal

  Entry Expression: "(oversold && trending) || bullish_cross"

This enters when EITHER:
  - RSI is below 30 AND ADX is above 25
  - OR MACD crosses above its signal line

Supported Expression Operators:
  - && or & : AND
  - || or | : OR
  - ! or ~  : NOT
  - ()      : Grouping


1.4 RUNNING A BACKTEST
----------------------

A backtest is executed by providing:

REQUIRED PARAMETERS:
  - strategy_id:      UUID of the strategy to test
  - ticker:           Symbol to trade (e.g., "AAPL", "BTCUSDT")
  - asset_class:      "STOCK" or "CRYPTO"
  - start_date:       Start of test period
  - end_date:         End of test period
  - initial_capital:  Starting capital amount

OPTIONAL PARAMETERS:

  Bar Resolution (bar_resolution):
    - "1m", "5m", "15m", "30m", "1h" (intraday)
    - "1d" (daily - default)
    - "1wk" (weekly)
    - "1mo" (monthly)

  Position Sizing (position_size_type, position_size_value):
    - "full_capital": Use all available cash (default)
    - "percent_capital": Use X% of total capital (value = percentage)
    - "fixed_amount": Use fixed dollar amount per trade (value = dollars)
    - "risk_based": Size based on risk percentage and stop distance
                    (value = risk % of equity to risk per trade)

      Risk-based sizing calculates position size as:
      Position Size = (Equity × Risk%) / Stop Distance%

      Example: $10,000 equity, 2% risk, 5% stop loss
      → Position Size = ($10,000 × 0.02) / 0.05 = $4,000

  Risk Management:
    - stop_loss_pct:    Exit if price drops X% from entry
    - take_profit_pct:  Exit if price rises X% from entry
    - dynamic_stop_loss: Indicator-based trailing stop (e.g., ATR-based)

  Transaction Costs:
    - commission_per_trade: Fixed cost per trade (e.g., $5)
    - commission_pct:       Percentage of trade value (e.g., 0.1%)
    - slippage_pct:         Price slippage on execution (e.g., 0.05%)

  Periodic Contributions:
    - amount:       Dollar amount to add
    - frequency:    "daily", "weekly", "monthly", "interval_days"
    - interval_days: Custom interval (if frequency = "interval_days")
    - include_start: Whether to contribute on first bar

  Attribution Analysis (enable_attribution):
    - true (default): Capture trade attribution data
    - false:          Skip attribution (slightly faster)

    When enabled, each trade captures:
    - Which conditions triggered entry/exit
    - Signal strength (0.0-1.0)
    - Market return during trade
    - Alpha (trade return - market return)
    - Indicator snapshots at entry/exit


1.5 UNDERSTANDING RESULTS
-------------------------

A completed backtest produces a comprehensive report:

PERFORMANCE METRICS:
  - total_return_pct:       Total percentage return
  - cagr:                   Compound Annual Growth Rate
  - sharpe_ratio:           Risk-adjusted return (annualized)
  - max_drawdown_pct:       Maximum peak-to-trough decline
  - longest_drawdown_days:  Longest time in drawdown

TRADE STATISTICS:
  - total_trades:           Number of completed trades
  - win_rate:               Percentage of profitable trades
  - avg_win:                Average profit on winning trades
  - avg_loss:               Average loss on losing trades
  - avg_win_loss:           Ratio of avg win to avg loss
  - profit_factor:          Gross profit / gross loss
  - largest_win:            Biggest single winning trade
  - largest_loss:           Biggest single losing trade
  - avg_trade_duration_days: Average time in a trade

FINAL VALUES:
  - final_capital:          Ending portfolio value

BENCHMARK COMPARISON:
  - benchmark_return_pct:      Buy-and-hold return
  - benchmark_final_capital:   Buy-and-hold ending value
  - benchmark_sharpe_ratio:    Buy-and-hold Sharpe ratio
  - benchmark_max_drawdown_pct: Buy-and-hold max drawdown
  - alpha:                     Strategy return - benchmark return
  - beta:                      Correlation with benchmark

TRADE LOG:
Each trade records:
  - entry_date, entry_price
  - exit_date, exit_price
  - shares traded
  - pnl (profit/loss in dollars)
  - pnl_pct (profit/loss percentage)
  - trade_duration_days
  - exit_reason: "signal", "stop_loss", "take_profit", "trailing_stop",
                 "force_close", "liquidation", or custom ExitRule name
                 (e.g., "rsi_20exit", "atr_signal_exit")

  Attribution fields (if enabled):
  - entry_conditions_met: List of condition UUIDs that triggered entry
  - exit_conditions_met: List of condition UUIDs that triggered exit
  - entry_signal_strength: Signal strength at entry (0.0-1.0)
  - market_return_during_trade: Buy-and-hold return for same period
  - alpha: Trade return - market return (skill vs luck)
  - indicator_snapshot_entry: All indicator values at entry
  - indicator_snapshot_exit: All indicator values at exit

ATTRIBUTION REPORT (Phase 1A):
Strategy-level insights when attribution is enabled:
  - total_alpha: Sum of alpha across all trades
  - alpha_percentage: What % of returns came from skill vs market
  - signal_strength breakdown:
    * Strong signals (>0.7): Count, win rate, avg alpha
    * Medium signals (0.3-0.7): Count, win rate, avg alpha
    * Weak signals (<0.3): Count, win rate, avg alpha
  - condition_frequency: How often each condition triggered

  Key Insight: Are your strong signals actually better performers?

BINNING ANALYSIS (Phase 1B):
Indicator validation report (requires 50+ trades):
  For each indicator used in entry conditions:
  - Quintile bins showing:
    * Value range (e.g., RSI 10-30)
    * Trade count in that range
    * Average P&L in that range
    * Win rate in that range
  - Spearman correlation (indicator value vs P&L)
  - Statistical significance (p-value)
  - Summary identifying strongest predictors

  Example: "RSI has -0.72 correlation (p<0.001) - lower RSI = higher profits"

  Key Insight: Which indicator ranges actually correlate with profitable trades?


1.6 SUPPORTED FEATURES
----------------------

A. ASSET CLASSES
   - STOCK: Equities (via Yahoo Finance)
   - CRYPTO: Cryptocurrencies (via Binance)

B. DATA PROVIDERS
   - YFinance: Stocks, ETFs, indices, and crypto (BTC-USD format)
     * Free tier, rate limited
     * Intraday data limited to 60 days for stocks
     * Adjusted for splits/dividends

   - Binance: Cryptocurrency pairs (BTCUSDT format)
     * Direct exchange data feed
     * Full historical depth
     * Multiple resolution support
     * IST timezone support

   Provider is automatically selected based on asset_class parameter.

C. TIME RESOLUTIONS
   Stocks: 1m, 2m, 5m, 15m, 30m, 60m, 90m, 1h, 1d, 5d, 1wk, 1mo, 3mo
   Crypto: 1m, 3m, 5m, 15m, 30m, 1h, 2h, 4h, 6h, 8h, 12h, 1d, 3d, 1w, 1mo

D. TECHNICAL INDICATORS
   - RSI (Relative Strength Index)
   - SMA (Simple Moving Average)
   - EMA (Exponential Moving Average)
   - MACD (Moving Average Convergence Divergence)
   - Bollinger Bands
   - ATR (Average True Range)
   - Stochastic Oscillator
   - ADX (Average Directional Index)
   - Ichimoku Cloud
   - ROC (Rate of Change)
   - OBV (On-Balance Volume)

E. POSITION SIZING METHODS
   - Full capital: Invests entire available cash balance
   - Percentage of capital: Fixed % of total equity (e.g., 10%)
   - Fixed dollar amount: Same dollar amount per trade
   - Risk-based: Size based on risk % and stop distance
                 Position Size = (Equity × Risk%) / Stop Distance%

F. RISK MANAGEMENT
   - Fixed stop loss (percentage from entry price)
   - Fixed take profit (percentage from entry price)
   - Dynamic trailing stop (indicator-based, e.g., ATR trailing)

G. TRANSACTION COSTS
   - Fixed commission per trade (e.g., $5)
   - Percentage commission (e.g., 0.1% of trade value)
   - Slippage simulation (percentage price impact)

H. PERIODIC CONTRIBUTIONS
   - Daily, weekly, monthly, or custom interval
   - Dollar-cost averaging simulation

I. ADVANCED LOGIC FEATURES
   - LOOKBACK operand: Compare current vs historical values
     Example: "rsi_14 > rsi_14:-5" (RSI higher than 5 bars ago)

   - Boolean expressions: Combine condition groups with &&, ||, !
     Example: "(oversold && trending) || breakout"

   - Crossover detection: CROSSES_ABOVE, CROSSES_BELOW operators
   - Trend detection: IS_RISING, IS_FALLING operators

J. ATTRIBUTION & VALIDATION (Phase 1A/1B)
   - Trade-level attribution: Track which conditions drive profitability
   - Signal strength scoring: Measure confluence (0.0-1.0)
   - Alpha calculation: Separate skill from market movement
   - Empirical binning: Validate indicator effectiveness with statistics
   - Correlation analysis: Spearman correlation per indicator
   - Significance testing: Identify statistically valid predictors

K. ROBUSTNESS ANALYSIS (Phase 2A)
   - Parameter sensitivity testing: Vary params by ±20%
   - Stability scoring: Coefficient of Variation across variants
   - Robustness classification: ROBUST / MODERATE / FRAGILE
   - Risk flag generation: Specific warnings about fragility
   - Parallel execution: Variant backtests run concurrently via Celery
   - Actionable recommendations: Deploy / caution / do not deploy

L. WALK-FORWARD VALIDATION (Phase 2B)
   - Divide historical data into N equal time windows
   - Run strategy independently on each window
   - Calculate consistency score (CV of returns/Sharpe/win_rate across windows)
   - Assess period-dependency (does the strategy only work in one era?)
   - Confidence levels: HIGH (20+ trades), MEDIUM (10-19), LOW (<10)

M. REGIME DETECTION (Phase 2C)
   - Pluggable segmentation strategies:
     * pelt_volatility: Returns + rolling vol → HIGH_VOL/LOW_VOL/TRANSITION
     * pelt_directional: Rolling mean → BULL/BEAR/CHOPPY/RANGING
     * l1_trend: L1 Trend Filter → BULL/BEAR
   - Analyze trades by regime (per-regime win rate, Sharpe, return)
   - Cross-regime trade analysis (trades spanning regime transitions)
   - Dependency scoring: INDEPENDENT / MODERATE / DEPENDENT

N. FEATURE CONDITIONING (Phase 2D)
   - Extract observable features at trade entry (volatility, trend_strength,
     price_vs_sma50, returns_autocorr, trend_slope, RSI, ATR%)
   - Bin features into quartiles
   - Identify winning conditions (feature ranges with >60% win rate)
   - Identify losing conditions (feature ranges with <40% win rate)
   - Feature importance ranking (variance of win rates across bins)

O. LEVERAGE
   - Binance-style isolated margin trading
   - Configurable multiplier (leverage=N in run_backtest)
   - Margin = position_value / leverage
   - Liquidation price calculated at entry
   - Liquidation fires as exit_reason="liquidation" with -100% PnL on margin
   - Works with both LONG and SHORT positions

P. SHORT SELLING
   - Dual position state machine (independent LONG and SHORT positions)
   - Direction-aware PnL: (entry - exit) * shares for shorts
   - Direction-aware stops: SL fires on price going UP for shorts
   - Direction-aware slippage: entry=sell (receive less), exit=buy (pay more)
   - Short-specific TP: exits when price drops X% from entry

Q. PLUGGABLE EXIT RULES
   - ExitRule dataclass: configurable per-bar exit conditions
   - Reference value captured at entry (frozen)
   - Monitor column checked each bar against reference
   - Activation gating: rule only active if ref meets threshold
   - Minimum loss gate: only fire if trade is losing >= N%
   - Skip column: per-bar boolean to suppress evaluation
   - Fixed threshold: compare monitor against static value (no ref_col needed)
   - Each trade stamps rule's name as exit_reason

R. DYNAMIC TAKE PROFIT
   - Per-bar TP percentage from a DataFrame column
   - Column provides custom TP level per position
   - Overrides static take_profit_pct when present

2.2 DATA FLOW PIPELINE
----------------------

When a backtest is executed, data flows through these stages:

STAGE 1: DATA FETCHING (data_layer.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. Check Redis cache for exact date range match                       │
│     └─ Hit? Return cached DataFrame                                    │
│                                                                        │
│  2. Check PostgreSQL for stored OHLCV bars                             │
│     └─ Covers range with sufficient bars? Return + cache               │
│                                                                        │
│  3. Fetch from external provider (yfinance/binance)                    │
│     └─ Normalize to standard format                                    │
│     └─ Store in PostgreSQL                                             │
│     └─ Cache in Redis                                                  │
│     └─ Return DataFrame                                                │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

STAGE 2: INDICATOR COMPUTATION (indicator_layer.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. Validate OHLCV columns present                                     │
│                                                                        │
│  2. For each indicator definition:                                     │
│     └─ Dispatch to pandas-ta function based on type                    │
│     └─ Handle multi-column outputs (MACD, BB, etc.)                    │
│     └─ Append to DataFrame with alias names                            │
│                                                                        │
│  3. Track indicator columns in DataFrame metadata                      │
│                                                                        │
│  4. Determine warmup period (first bar where all indicators valid)     │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

STAGE 3: WARMUP TRIMMING (indicator_layer.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. Find first bar where ALL indicator columns have valid values       │
│     (not NaN)                                                          │
│                                                                        │
│  2. Trim DataFrame to remove warmup period                             │
│                                                                        │
│  3. Validate sufficient bars remain (minimum 30)                       │
│                                                                        │
└────────────────────────────────────────────────────────────────────────┘

STAGE 4: CONDITION EVALUATION (condition_engine.py)
┌────────────────────────────────────────────────────────────────────────┐
│                                                                        │
│  1. For each condition in a group:                                     │
│     └─ Resolve left operand to Series/scalar (INDICATOR/OHLCV/SCALAR) │
│     └─ Resolve right operand to Series/scalar (or LOOKBACK)           │
│     └─ Apply operator (GT/LT/CROSSES_ABOVE/IS_RISING) → Boolean Series│
│                                                                        │
│  2. Combine conditions with group logic (AND/OR)                       │
│                                                                        │
│  3. If using boolean expressions:                                      │
│     └─ Evaluate each named group independently                         │
│     └─ Build namespace mapping group names to boolean results          │
│     └─ Execute boolean expression (&&, ||, !, parentheses)             │
│     └─ Return final boolean signal                                     │
│                                                                        │
│  4. If attribution enabled:                                            │
│     └─ Track which conditions evaluated to True                        │

Purpose: Simulate trade execution with realistic fills

Full Signature:
  run_backtest(

      periodic_contribution: dict | None = None,
      position_size_type: str = "full_capital",
      position_size_value: float = 100.0,
      stop_loss_pct: float | None = None,
      take_profit_pct: float | None = None,
      dynamic_stop_column: str | None = None,
      dynamic_tp_pct_column: str | None = None,
      dynamic_exit_monitor_column: str | None = None,
      dynamic_exit_ref_column: str | None = None,
      dynamic_exit_skip_column: str | None = None,
      dynamic_exit_min_loss_pct: float | None = None,
      commission_per_trade: float = 0.0,
      commission_pct: float = 0.0,
      slippage_pct: float = 0.0,
      enable_attribution: bool = True,
      entry_conditions: dict | None = None,
      exit_conditions: dict | None = None,

      short_exit_signal: pd.Series | None = None,
      short_entry_conditions: dict | None = None,
      short_exit_conditions: dict | None = None,
      leverage: float = 1.0,
      exit_rules: list | None = None,
  ) → tuple[list[dict], pd.Series]

Key Parameters:
  - asset_class: "STOCK" (whole shares) or "CRYPTO" (fractional)
  - position_size_type/value: How to size positions
  - stop_loss_pct, take_profit_pct: Risk management
  - dynamic_stop_column: Indicator-based trailing stop
  - dynamic_tp_pct_column: Per-bar dynamic TP from DataFrame column
  - dynamic_exit_*: Legacy dynamic exit (monitor vs ref comparison)
  - commission_per_trade, commission_pct: Transaction costs
  - slippage_pct: Price slippage simulation
  - periodic_contribution: Regular cash additions
  - enable_attribution: Enable trade attribution tracking (default: True)
  - short_entry_signal/short_exit_signal: Independent short signals
  - leverage: Position multiplier (1.0 = no leverage)
  - exit_rules: List of ExitRule objects for pluggable exits

State Machine Logic:
  1. NO_POSITION: Check for entry signal (long or short)
     → If True, set pending_entry = True on appropriate PositionState
     → If attribution enabled: capture entry conditions met

  2. PENDING_ENTRY: At next bar open
     → Calculate position size (with leverage multiplier if set)
     → Apply slippage to price (direction-aware)
     → Deduct cost + commission from cash (margin for leveraged)
     → Calculate liquidation price (if leverage > 1.0)
     → Capture exit_rule_states (freeze ref values from ExitRule objects)
     → Record entry_date, entry_price, shares
     → If attribution enabled: capture entry attribution data

  3. IN_POSITION: Check for exit conditions (priority order)
     a. Liquidation check (leveraged positions, bar low/high vs liquidation_price)
     b. Pluggable exit rules (per-bar evaluation, each rule checked in order)
     c. Dynamic stop (indicator-based trailing stop)
     d. Stop loss triggered (price dropped X% from entry)
     e. Take profit triggered (price gained X%, or dynamic TP)
     f. Strategy exit signal
     → Set pending_exit = True, stamp exit_reason
     → If attribution enabled: capture exit conditions met

  4. PENDING_EXIT: At next bar open
     → Apply slippage to exit price (direction-aware)
     → Deduct commission
     → Calculate proceeds (leveraged: margin + PnL, clamped to 0)
     → Add proceeds to cash
     → Record trade in trade_log with exit_reason
     → If attribution enabled: calculate market return, alpha

  DUAL POSITION STATE:
  The engine maintains two independent PositionState objects:
    long_pos = PositionState(direction="LONG")
    short_pos = PositionState(direction="SHORT")
  They are evaluated independently each bar, allowing simultaneous
  long and short positions.

Leverage Mechanics:
  - Entry: shares = base_shares × leverage
  - Margin deducted = (shares × price) / leverage + commission
  - Liquidation price (LONG):  entry_price × (1 - 1/leverage)
  - Liquidation price (SHORT): entry_price × (1 + 1/leverage)
  - Exit proceeds = max(0, margin + unrealized_PnL) - commission
  - Liquidation: entire margin is lost, PnL = -(margin + entry_commission)

Mark-to-Market:
  - Unleveraged LONG: shares × current_price
  - Unleveraged SHORT: shares × (2 × entry_price - current_price)
  - Leveraged: max(0, margin + unrealized_PnL)

Position Sizing Logic:
  - full_capital: shares = cash / price
  - percent_capital: shares = (total_capital * pct / 100) / price
  - fixed_amount: shares = fixed_dollars / price
  - risk_based: shares = (equity * risk_pct) / (entry - stop)

Commission Handling:
  - Fixed: commission_per_trade
  - Percentage: commission_pct / 100 * (shares * price)
  - Total: fixed + percentage
  - Applied on both entry and exit

Slippage Handling (direction-aware):
  - LONG entry (buy):  price × (1 + slippage_pct / 100)  → pay more
  - LONG exit (sell):  price × (1 - slippage_pct / 100)  → receive less
  - SHORT entry (sell): price × (1 - slippage_pct / 100) → receive less
  - SHORT exit (buy):   price × (1 + slippage_pct / 100) → pay more

TradeRecord Structure:

4.4 PARAMETER SENSITIVITY ANALYSIS (Phase 2A)
---------------------------------------------

PURPOSE:
Identify fragile vs robust strategies by testing how performance changes when
indicator parameters are varied. A robust strategy maintains similar performance
across parameter variations; a fragile strategy's performance swings wildly,
suggesting overfitting to specific parameter values.

THE PROBLEM IT SOLVES:
Traders often "optimize" indicator parameters to maximize backtest returns.
This creates a false sense of confidence - the strategy works great on historical
data with those exact parameters, but fails in live trading when market
conditions shift slightly. Parameter sensitivity analysis exposes this risk.

HOW IT WORKS:
1. Takes your strategy with its indicator parameters (e.g., RSI period=14)
2. Generates variants by varying each numeric parameter by ±variation_pct
   (default ±20%)
   Example: RSI(14) generates RSI(11) and RSI(17)
3. Runs baseline backtest + all variant backtests in parallel via Celery
4. Collects key metrics from each variant (return, Sharpe, win rate, etc.)
5. Calculates stability score using Coefficient of Variation (CV)
6. Classifies strategy robustness level

STABILITY SCORE CALCULATION:
For each metric (total_return_pct, sharpe_ratio, win_rate):
  1. Collect values from baseline + all variants
  2. Calculate Coefficient of Variation: CV = std_dev / |mean|
  3. Average CVs across metrics: mean_CV
  4. Stability Score = max(0, min(1, 1 - mean_CV))

INTERPRETATION:
  - CV close to 0: Metrics are stable across variants
  - CV > 1: Metrics swing more than 100% from the mean
  - Stability Score 1.0: Perfect stability (all variants same)
  - Stability Score 0.0: Extreme instability (huge variation)

ROBUSTNESS CLASSIFICATION:
  - ROBUST (score ≥ 0.8): Metrics vary < 20% across variants
    → Safe to deploy with confidence

  - MODERATE (score 0.6-0.8): Metrics vary 20-40%
    → Use with caution; consider tighter parameter ranges

  - FRAGILE (score < 0.6): Metrics vary > 40%
    → DO NOT DEPLOY; suggests overfitting to specific parameters

where small errors don't cause large performance swings.

4.5 WALK-FORWARD VALIDATION (Phase 2B)
---------------------------------------

PURPOSE:
Detect period-dependency by testing if a strategy works consistently across
different time windows. Unlike walk-forward optimization (which re-fits params),
this uses FIXED parameters and simply validates consistency.

THE PROBLEM IT SOLVES:
A strategy may show 80% return over 3 years, but if 75% of that came from a
single 6-month bull run, it's useless in other market conditions. Walk-forward
validation splits the data into windows and checks if performance is stable
across all of them.

HOW IT WORKS:
1. Fetch full date range OHLCV data
2. Compute indicators ONCE on the full dataset (avoids warmup loss per window)
3. Divide into N equal windows by bar count (default: 5)
4. Run the same strategy on each window independently
5. Calculate consistency score from per-window metrics
6. Assess period-dependency

WINDOW GENERATION (generate_windows):
  Divides DataFrame into N equal windows by bar count.
  Remainder bars are distributed across the first N windows (one extra each).

  Example: 1000 bars, 5 windows
    Window 1: bars 0-199   (200 bars)
    Window 2: bars 200-399 (200 bars)
    Window 3: bars 400-599 (200 bars)
    Window 4: bars 600-799 (200 bars)
    Window 5: bars 800-999 (200 bars)

  Each Window dataclass contains:
    - index: Window number (1-based)
    - start_idx, end_idx: Bar index range
    - start_date, end_date: Calendar dates

CONSISTENCY SCORE CALCULATION (calculate_consistency_score):
  Uses Coefficient of Variation across windows, same methodology as
  parameter sensitivity (Section 4.4).

  Evaluated metrics: total_return_pct, sharpe_ratio, win_rate

  For each metric:
    1. Collect values from all windows with >= min_trades (default 10)
    2. Calculate CV = std_dev / |mean|
    3. Cap CV at 1.0

  Overall score = 1.0 - mean(CVs)

  Returns: (score, per_metric_cv_dict)

CONFIDENCE LEVELS:
  Per-window confidence based on trade count:
  - HIGH: 20+ trades → reliable metrics
  - MEDIUM: 10-19 trades → interpret with caution
  - LOW: <10 trades → excluded from consistency score calculation

ASSESSMENT (assess_walk_forward_results):
  Classification:
  - ROBUST: score >= 0.8 AND >= 80% windows profitable
  - MODERATE: score >= 0.6 AND >= 60% windows profitable
  - FRAGILE: otherwise

  Risk flags generated when:
  - Strategy unprofitable in > 50% of windows
  - > 40% of windows had insufficient trades
  - Consistency score < 0.5 (high variance)
  - Worst window lost > 10%

4.6 REGIME DETECTION (Phase 2C)
-------------------------------

PURPOSE:
Detect market regimes (trend, volatility, ranging) and analyze whether strategy
performance depends on the current regime. If a strategy only profits in bull
markets, you need to know that before deploying.

THE PROBLEM IT SOLVES:
Most strategies are implicitly coupled to market conditions. A mean-reversion
strategy may work in ranging markets but get destroyed in trends. Regime detection
quantifies this dependency so you can either:
  - Add regime filters (only trade when regime is favorable)
  - Develop regime-specific strategies
  - Adjust position sizing based on current regime

ARCHITECTURE:
  Strategy Pattern (Pluggable Segmentation):

    ┌─────────────────────────────────────────────────────────────┐
    │                  SegmentationStrategy (ABC)                   │
    │  detect_changepoints(df, penalty, min_segment_length)        │
    │  compute_segment_features(df, start_idx, end_idx)            │
    │  label_segments(df, changepoints) → list[LabeledSegment]     │
    │  get_strategy_name() → str                                   │
    │  get_regime_types() → list[str]                              │
    └─────────────────────────────────────────────────────────────┘
                              ▲
         ┌────────────────────┼────────────────────┐
         │                    │                    │
    ┌────┴────┐        ┌─────┴─────┐       ┌─────┴─────┐
    │Volatility│        │Directional│       │ L1 Trend  │
    │ Strategy │        │ Strategy  │       │ Strategy  │
    └─────────┘        └───────────┘       └───────────┘

  SegmentationFactory:
    SegmentationFactory.create_strategy(name, **kwargs)
    Supported: "l1_trend", "pelt_directional", "pelt_volatility"

SEGMENTATION STRATEGIES:

  1. PELT Volatility ("pelt_volatility")
     Signal: [log_returns, rolling_vol] (bivariate)
     Detection: PELT changepoint detection on volatility regime shifts
     Regimes: HIGH_VOL, LOW_VOL, TRANSITION
     Use case: Identify when volatility environment shifts

  2. PELT Directional ("pelt_directional")
     Signal: rolling_mean(log_returns)
     Detection: PELT on rolling price momentum
     Labeling: OLS regression per segment → SNR-based classification
     Regimes: BULL, BEAR, CHOPPY, RANGING
     Parameters:
       - r2_mode: "percentile" or "fixed"
       - r2_percentile: Threshold for directional vs sideways (default 75)
       - r2_fixed: Fixed R² threshold (default 0.3)
     Use case: Identify trending vs sideways markets

  3. L1 Trend Filter ("l1_trend")
     Signal: L1-regularized trend (piecewise linear approximation)
     Detection: NOT PELT-based; uses L1 optimization to find trend
     Labeling: Slope of fitted trend → positive = BULL, negative = BEAR
     Regimes: BULL, BEAR (2 only, binary)
     Parameters:
       - k: Smoothing parameter (default 0.015), range 0.01-0.03
         Higher k = smoother trend (fewer regime changes)
     Use case: Clean directional regime without noise

CORE DATA STRUCTURES:

  @dataclass

      end_idx: int        # Exclusive

      features: dict[str, float]

ANALYSIS FUNCTIONS:

4.7 FEATURE CONDITIONING (Phase 2D)
------------------------------------

PURPOSE:
Extract observable market features at trade entry time and discover which
feature ranges predict trade success. Produces actionable conditions like:
"Trade when volatility ∈ [0.015, 0.025] AND trend_strength > 0.7"

KEY DIFFERENCE FROM REGIME DETECTION:
  - Regime detection: Labels entire periods as BULL/BEAR (backward-looking,
    descriptive, only known after the fact)
  - Feature conditioning: Measures raw features at entry time (forward-looking,
    predictive, computable in real-time for trade filtering)

THE PROBLEM IT SOLVES:
Your strategy has 55% win rate overall, but the 55% is an average across
very different market states. Feature conditioning reveals that:
  - When volatility is in [0.015, 0.025]: win rate = 72%
  - When volatility > 0.04: win rate = 31%
This gives you a real-time filter: only take trades when volatility is in
the sweet spot.

FEATURES EXTRACTED (all computable in real-time):

  volatility: Rolling std of log returns over lookback window
    → Measures current market noise level

  trend_strength: R² from OLS regression of log(close) over lookback
    → 0.0 = no trend (random walk), 1.0 = perfect linear trend

  trend_slope: OLS slope of log(close)
    → Positive = uptrend, negative = downtrend, magnitude = rate

  price_vs_sma50: (close - SMA50) / SMA50
    → Relative position vs 50-bar moving average
    → Positive = above MA, negative = below

  returns_autocorr: Lag-1 autocorrelation of returns
    → Negative = mean-reverting, positive = trending, near 0 = random

  rsi_level: RSI at entry (if strategy uses RSI indicator)
    → Optional, auto-detected from DataFrame columns

  atr_pct: ATR / price (if strategy uses ATR indicator)
    → Normalized volatility measure, optional

FEATURE EXTRACTION (extract_features_at_index):
  Takes DataFrame and bar index, uses lookback_window (default 50 bars).
  Returns FeatureVector dataclass with all computed features.
  Handles edge cases: insufficient data returns neutral values (0.0).

QUARTILE BINNING (bin_feature):
  Divides feature values into N quantile bins (default 4 = quartiles).
  Returns bin_indices and bin_ranges.
  Handles degenerate cases (all same value, too few data points).

CONDITION ANALYSIS (analyze_feature_conditions):
  For each feature:
    1. Collect feature values and trade outcomes (win/loss, PnL)
    2. Bin into quartiles
    3. Calculate per-bin metrics: win_rate, avg_pnl_pct, Sharpe
    4. Identify winning conditions (win_rate >= 60%)
    5. Identify losing conditions (win_rate <= 40%)

  Feature importance = normalized std(win_rates across bins)
    Higher std = feature has more predictive power
    0.0 = no differentiation between bins
    1.0 = maximum differentiation (best bin vs worst bin)

  Minimum trades per bin: default 10 (configurable via min_trades_per_bin)
  Confidence levels: HIGH (20+ trades per bin), MEDIUM (10-19)

4.8 LEVERAGE SYSTEM
-------------------

PURPOSE:
Simulate leveraged trading with Binance-style isolated margin mechanics.
Allows testing strategies with amplified exposure while accounting for
liquidation risk.

HOW IT WORKS:

  Entry:
    1. Calculate base position size (from position_size_type/value)
    2. Multiply shares by leverage factor: shares = base_shares × leverage
    3. Margin deducted from cash = (shares × price) / leverage + commission
       (NOT the full notional value)
    4. Calculate liquidation price:
       - LONG: entry_price × (1 - 1/leverage)
       - SHORT: entry_price × (1 + 1/leverage)

  Example: $10,000 capital, 50% position size, 10x leverage
    Base amount: $5,000 (50% of capital)
    Shares (without leverage): 5000 / price
    Shares (with 10x): 50,000 / price ← controls 10x notional
    Margin deducted: $5,000 (the actual cash used)
    Liquidation price (LONG): price × 0.90 (10% below entry)

  In-Position:
    Each bar, check if bar_low (LONG) or bar_high (SHORT) breaches
    liquidation price. If breached:
    - Trade exits immediately at liquidation_price
    - PnL = -(margin + entry_commission) → -100% of invested capital
    - exit_reason = "liquidation"
    - No exit commission charged (exchange seized the margin)

  Exit (non-liquidation):
    proceeds = max(0, margin + unrealized_PnL) - exit_commission
    PnL = proceeds - margin - entry_commission
    pnl_pct = PnL / (margin + entry_commission)

  Mark-to-Market:
    Equity = cash + max(0, margin + unrealized_PnL)
    Clamped to 0 because you can't owe more than your margin (isolated margin)

INTERACTION WITH OTHER FEATURES:
  - Stop loss: Still fires based on percentage from entry. With 10x leverage,
    a 5% stop = 50% loss on margin. If stop is set larger than 1/leverage,
    liquidation fires first.
  - Exit rules: Evaluated before liquidation check in priority order.
    If an exit rule has min_loss_pct < 100/leverage, it fires before liquidation.
  - Position sizing: With percent_capital=50 and leverage=10, you put 50% of
    capital as margin and control 5x of total capital in notional value.

PARAMETER:
  leverage: float = 1.0 (default: no leverage)
  Pass to run_backtest() or as part of smoke script configuration.

IMPORTANT NOTES:
  - Isolated margin only (no cross-margin)
  - No funding rates simulated
  - Liquidation is instantaneous (no partial liquidation ladder)
  - Works with both LONG and SHORT positions


4.9 SHORT SELLING
-----------------

PURPOSE:
Enable short positions (profit from price drops) with a fully independent
state machine. Supports simultaneous long and short positions.

HOW IT WORKS:

  Activation:
    Pass short_entry_signal and short_exit_signal to run_backtest().
    If short_entry_signal is provided (not None), short selling is active.
    When not provided, the engine operates in long-only mode (backward compatible).

  Dual State Machine:
    long_pos = PositionState(direction="LONG")
    short_pos = PositionState(direction="SHORT")

    Both are evaluated independently each bar. You can be long AND short
    simultaneously (useful for hedging or independent signal systems).

  SHORT Entry Flow:
    1. short_entry_signal fires on bar N
    2. Engine sets short_pos.pending_entry = True
    3. Bar N+1: fill at open price
       - Slippage: price × (1 - slippage_pct/100) → sell at lower price
       - Cash deducted = shares × entry_price + commission (collateral)
       - If leverage > 1.0: margin = notional / leverage

  SHORT Exit Flow:
    1. short_exit_signal, stop_loss, take_profit, exit_rule, or force_close
    2. Engine sets short_pos.pending_exit = True
    3. Next bar: fill at open price
       - Slippage: price × (1 + slippage_pct/100) → buy back at higher price
       - PnL = (entry_price - exit_price) × shares - commissions
       - Proceeds = shares × (2 × entry_price - exit_price) - commission

  Direction-Aware Stop/TP:
    - Stop loss (SHORT): fires when price goes UP by stop_loss_pct%
      sl_price = entry_price × (1 + stop_loss_pct/100)
      Triggers when bar_high >= sl_price
    - Take profit (SHORT): fires when price goes DOWN by take_profit_pct%
      tp_price = entry_price × (1 - take_profit_pct/100)
      Triggers when bar_low <= tp_price
    - Dynamic stop (SHORT): fires when price crosses ABOVE stop indicator

  Direction-Aware Mark-to-Market:
    MTM = shares × (2 × entry_price - current_price)
    When price drops: MTM increases (profit)
    When price rises: MTM decreases (loss)

PARAMETERS:
  short_entry_signal: pd.Series | None = None
  short_exit_signal: pd.Series | None = None
  short_entry_conditions: dict | None = None  (for attribution)
  short_exit_conditions: dict | None = None   (for attribution)

EXAMPLE USAGE:
  trades, equity = run_backtest(
      df=df,
      entry_signal=long_entry_signal,
      exit_signal=long_exit_signal,
      short_entry_signal=short_entry_signal,
      short_exit_signal=short_exit_signal,
      initial_capital=10000,
      take_profit_pct=5.0,    # 5% for longs, 5% drop for shorts
      leverage=5.0,           # Works with both directions
  )


4.10 PLUGGABLE EXIT RULES
--------------------------

PURPOSE:
Allow per-bar evaluation of custom exit conditions beyond simple stop/TP.
Exit rules capture a reference value at entry time and compare a monitor
column against it each bar, with optional gating by activation threshold
and minimum loss requirement.

THE PROBLEM IT SOLVES:
Fixed stops and TPs are one-size-fits-all. Real strategies need nuanced exits:
  - "Exit if RSI crosses below the ATR mean it was at when we entered"
  - "Exit if volatility doubles from entry level, but only if we're losing 1%+"
  - "Exit if RSI drops below 30 (fixed threshold), but only when ATR confirms"

ExitRule DATACLASS (app/engine/exit_rules.py):

  @dataclass
  class ExitRule:
      name: str = "exit_rule"
        # Stamps exit_reason on the trade record

      ref_col: str = ""
        # Column to capture at entry (frozen reference value)
        # Ignored when fixed_threshold is set

      monitor_col: str = ""
        # Column checked every bar against reference

      operator: str = "LT"
        # "LT" or "GT" comparison of monitor vs reference
        # "LT": fires when monitor < ref (e.g., RSI drops below entry level)
        # "GT": fires when monitor > ref (e.g., vol spikes above entry level)

      activation_threshold: float | None = None
        # Gate: rule only active if ref_col value at entry meets this threshold
        # Combined with activation_operator

      activation_operator: str = "LT"
        # "LT": active if ref_value < activation_threshold
        # "GT": active if ref_value > activation_threshold

      min_loss_pct: float | None = None
        # Only fire if trade is losing >= this percentage
        # Prevents premature exits on winning trades

      skip_col: str | None = None
        # Per-bar boolean column to suppress evaluation
        # When True at current bar, rule is skipped

      fixed_threshold: float | None = None
        # Compare monitor_col against this static value instead of ref_col
        # When set, no ref_col capture needed (ref stored as fixed_threshold)

LIFECYCLE:

  1. CAPTURE (_capture_exit_rule_states, called after entry fill):
     For each ExitRule:
       - If fixed_threshold set: store {ref_value: fixed_threshold, active: True}
       - Else: capture df[ref_col] at entry_bar_idx
         - If activation_threshold set: check if captured value meets gate
         - Store {ref_value: captured_val, active: bool}
     Result stored in pos.exit_rule_states (list of dicts)

  2. CHECK (_check_exit_rules, called each bar while in position):
     For each ExitRule and its state:
       - Skip if not active or ref_value is None
       - Skip if monitor_col not in DataFrame
       - Skip if skip_col evaluates to True at current bar
       - Read monitor_val = df[monitor_col] at current bar
       - Compare: "LT" → monitor < ref, "GT" → monitor > ref
       - If not triggered: continue to next rule
       - If triggered AND min_loss_pct set:
         - Calculate current PnL% (direction-aware)
         - Only fire if PnL% <= -|min_loss_pct|
       - If all checks pass: set pending_exit, stamp rule.name as exit_reason
       - First matching rule wins (rules checked in order)

EXAMPLE CONFIGURATIONS:

  # Exit if RSI drops below 30 and we're losing 1%+
  ExitRule(
      name="rsi_30_exit",
      monitor_col="rsi_14",
      fixed_threshold=30.0,
      operator="LT",
      min_loss_pct=1.0,
  )

  # Exit if current ATR exceeds the ATR mean at entry
  # Only active if ATR mean at entry was below 500
  ExitRule(
      name="atr_signal_exit",
      ref_col="atr_mean_24",
      monitor_col="atr_14",
      operator="GT",
      activation_threshold=500.0,
      activation_operator="LT",
      min_loss_pct=1.0,
      skip_col="skip_atr_exit",
  )

  # Simple fixed: exit if RSI goes above 80
  ExitRule(
      name="overbought_exit",
      monitor_col="rsi_14",
      fixed_threshold=80.0,
      operator="GT",
  )

PARAMETER:
  exit_rules: list[ExitRule] | None = None
  Pass list to run_backtest(). Each rule evaluated per bar in order.

INTERACTION WITH OTHER EXITS:
  Priority order in engine:
  1. Liquidation (leveraged positions only)
  2. Exit rules (evaluated in list order, first match wins)
  3. Dynamic stop (indicator trailing stop)
  4. Percentage stop loss
  5. Percentage take profit / dynamic TP
  6. Signal exit

  Once any exit triggers, the position goes to PENDING_EXIT and no
  further exit checks run.


4.11 DYNAMIC TAKE PROFIT
-------------------------

PURPOSE:
Allow per-bar dynamic take-profit percentage from a DataFrame column,
enabling position-specific or market-adaptive TP levels.

HOW IT WORKS:
  - Pass dynamic_tp_pct_column (column name in df) to run_backtest()
  - Each bar, if column has a valid value at current bar, use it as TP%
  - Overrides static take_profit_pct when the column value is available
  - Falls back to static take_profit_pct if column value is NaN

PARAMETER:
  dynamic_tp_pct_column: str | None = None

EXAMPLE:
  # Column "dynamic_tp" varies per bar based on ATR
  df["dynamic_tp"] = df["atr_14"] / df["close"] * 100 * 2  # 2x ATR as %

  trades, equity = run_backtest(
      df=df,
      entry_signal=signal,
      exit_signal=exit_signal,
      initial_capital=10000,
      take_profit_pct=5.0,              # Fallback static TP
      dynamic_tp_pct_column="dynamic_tp", # Per-bar override
  )

IMPLEMENTATION:
  In _check_stops(), at the TP evaluation:
  - Read dynamic_tp_pct from pos.dynamic_tp_pct (captured at entry from column)
  - If present, use it; otherwise fall back to take_profit_pct parameter
  - TP price calculated same way: entry × (1 ± dynamic_tp/100)
