================================================================================
                    ARCHITECTURE: BACKTEST vs LIVE TRADING
================================================================================

CURRENT: Backtest Architecture
-------------------------------

Flow:
  User → API → Celery Task → Engine (batch) → Database

  1. User submits backtest via API
  2. Celery task fetches ALL historical data
  3. Computes ALL indicators on full DataFrame
  4. Evaluates ALL conditions on full DataFrame
  5. Iterates bar-by-bar through DataFrame simulating trades
  6. Returns complete report at end

Characteristics:
  - Synchronous bar iteration
  - Complete dataset in memory
  - No real-time constraints
  - Perfect information (full history available)


FUTURE: Live Trading Architecture
----------------------------------

Flow:
  User → API → TradingSession → Event Loop → Broker

  1. User starts live trading session via API
  2. TradingSession subscribes to real-time data feed (WebSocket)
  3. On each new bar:
     a. Update indicators incrementally
     b. Evaluate entry/exit conditions
     c. Check risk limits
     d. Place/cancel orders via broker API
  4. On order fill:
     a. Update position state
     b. Update equity tracking
     c. Log trade to database
  5. Continuous loop until stopped

Characteristics:
  - Event-driven (asynchronous)
  - Streaming data (one bar at a time)
  - Real-time constraints (must react within seconds)
  - Partial information (no future data, only past + current)


Key Differences:
---------------

Aspect              | Backtest             | Live Trading
--------------------|----------------------|---------------------------
Data                | Batch (full history) | Stream (real-time)
Execution           | Simulated fills      | Real broker orders
Latency             | Seconds to minutes   | <1 second critical
Errors              | Retry entire run     | Handle gracefully, continue
State               | Stateless iteration  | Stateful session
Parallelism         | One task at a time   | Many sessions concurrently

Challenge 1: Indicator Warmup on Live Start
--------------------------------------------
Problem:
  - RSI_14 needs 14 bars to initialize
  - SMA_200 needs 200 bars to initialize
  - When live session starts, indicators will be NaN initially

Solution:
  1. On session start, fetch last 500 bars of historical data
  2. Compute indicators on historical data (backfill)
  3. When real-time bars arrive, update indicators incrementally
  4. Mark session as "WARMING_UP" until all indicators initialized
  5. Only start trading after warmup complete

Code:
```python
async def start_live_session(session_id):
    session = await get_session(session_id)

    # Fetch historical bars for warmup
    df_history = await fetch_ohlcv_async(
        session.ticker,
        start=today - 500 bars,
        end=now
    )

    # Initialize indicators
    df_history = compute_indicators(df_history, session.strategy.indicators)

    # Store indicator state (last 200 rows for rolling calculations)
    session.indicator_buffer = df_history.tail(200)
    session.status = "READY"

    # Now start real-time feed
    await realtime_feed.subscribe(session.ticker)
```


Challenge 2: Race Conditions (Order Fill vs New Bar)
-----------------------------------------------------
Problem:
  - New bar arrives: "Entry signal triggered, place order"
  - Order fill arrives: "Position opened"
  - Another new bar arrives: "Entry signal triggered again!"
  - System tries to enter twice

Solution:
  - Use async locks to prevent concurrent signal processing
  - Track order state: PENDING_ENTRY_ORDER, IN_POSITION
  - Ignore entry signals while PENDING_ENTRY_ORDER
  - Only process exit signals when IN_POSITION

Code:
```python
class TradingSession:
    def __init__(self):
        self.state = "NO_POSITION"
        self.lock = asyncio.Lock()

    async def on_bar(self, bar):
        async with self.lock:  # Prevent concurrent processing
            if self.state == "NO_POSITION":
                if self.check_entry_signal():
                    await self.place_entry_order()
                    self.state = "PENDING_ENTRY_ORDER"

            elif self.state == "IN_POSITION":
                if self.check_exit_signal():
                    await self.place_exit_order()
                    self.state = "PENDING_EXIT_ORDER"

    async def on_order_fill(self, order):
        async with self.lock:
            if order.reason == "ENTRY":
                self.state = "IN_POSITION"
            elif order.reason == "EXIT":
                self.state = "NO_POSITION"
```


Challenge 3: WebSocket Disconnections
--------------------------------------
Problem:
  - Exchange WebSocket disconnects
  - Miss bars during reconnection
  - Indicators now out of sync

Solution:
  - Detect disconnect immediately
  - Fetch missed bars via REST API (gap fill)
  - Recompute indicators on gap-filled data
  - Resume real-time feed

Code:
```python
async def handle_websocket_disconnect():
    logger.warning("WebSocket disconnected, attempting recovery")

    # Get last received bar timestamp
    last_bar_time = session.indicator_buffer.index[-1]

    # Reconnect WebSocket
    await realtime_feed.reconnect()

    # Fetch missed bars via REST
    now = datetime.utcnow()
    if now - last_bar_time > timedelta(minutes=1):
        gap_bars = await fetch_ohlcv_rest(
            ticker=session.ticker,
            start=last_bar_time,
            end=now
        )

        # Update indicators with gap data
        for bar in gap_bars:
            session.update_indicators_incremental(bar)

    logger.info("WebSocket reconnected and synced")
```


Challenge 4: Latency & Execution Speed
---------------------------------------
Problem:
  - Signal triggers at 10:30:00.000
  - Indicator calculation takes 50ms
  - Condition evaluation takes 20ms
  - Broker order submission takes 100ms
  - Order fill at 10:30:00.170 → Price moved!

Solution:
  1. Pre-compute what you can (indicator configs cached)
  2. Use vectorized operations (NumPy, not loops)
  3. Async I/O for broker calls (don't block)
  4. Accept slippage as reality (model it realistically)
  5. For HFT: Not suitable (Python has ~100ms overhead)
  6. For swing/position trading: Perfectly fine

Target Latency:
  - Signal detection: <50ms
  - Order submission: <200ms
  - Total: <250ms (acceptable for timeframes >= 1 minute)


Challenge 5: Multiple Sessions Concurrently
--------------------------------------------
Problem:
  - User runs 10 strategies on different tickers
  - Each session needs own WebSocket, indicator state, event loop
  - Resource contention

Solution:
  - Each TradingSession is a separate async task
  - Use asyncio.gather() to run concurrently
  - Share WebSocket connections when possible (same exchange)
  - Use Redis for shared state (equity tracking)
  - Celery beat for periodic tasks (equity snapshots)

Code:
```python
# In app startup
async def start_all_active_sessions():
    sessions = await db.query(LiveTradingSession).filter(status="ACTIVE").all()

    tasks = [
        run_trading_session(session.id)
        for session in sessions
    ]

    await asyncio.gather(*tasks)


async def run_trading_session(session_id):
    """Each session runs independently"""
    session = await load_session(session_id)

    while session.status == "ACTIVE":
        bar = await realtime_feed.get_next_bar(session.ticker)
        await session.on_bar(bar)
```



================================================================================
                    RISK ASSESSMENT & SAFETY MEASURES
================================================================================

Risks:
------
1. 🔴 CRITICAL: Real money at stake - bugs can cause financial loss
2. 🔴 CRITICAL: Order duplication - double entry due to race condition
3. 🟡 HIGH: Runaway trading - strategy goes haywire, places 1000 orders
4. 🟡 HIGH: Data quality - bad tick causes wrong indicator, wrong signal
5. 🟡 MEDIUM: API rate limits - get banned from exchange
6. 🟡 MEDIUM: Credential leak - broker API keys exposed

Safety Measures:
---------------

1. Paper Trading Mandatory First
   - Require 30 days paper trading before LIVE mode unlocked
   - Display paper vs live results side-by-side
   - Force user to acknowledge risks

2. Position Size Limits
   - Max 10% of capital per trade (configurable)
   - Max 3 concurrent positions
   - Max $10,000 per order (adjustable)

3. Circuit Breakers
   - Max 5% drawdown per day → halt all trading
   - Max 10 trades per day → stop after limit
   - Max 3 consecutive losses → pause for review

4. Order Validation
   - Pre-flight checks before every order:
     * Sufficient balance?
     * Position size within limits?
     * Not already in position?
     * Market open? (for stocks)
   - Rate limit: Max 1 order per second per session

5. Credential Security
   - Encrypt broker API keys at rest (AES-256)
   - Never log API keys
   - Use environment variables, not database
   - Require 2FA for live trading

6. Monitoring & Alerts
