ARCHITECTURE COMPARISON: ta4j vs backtest-engine
================================================================================
Generated: 2026-07-08
Based on: Deep research of ta4j v0.23.0 + full audit of backtest-engine

================================================================================
EXECUTIVE SUMMARY
================================================================================

**Philosophy Alignment:**
- Both engines prioritize deterministic backtesting with lookahead-bias prevention
- Both use bar-by-bar sequential processing (not vectorized)
- Both support pluggable components for extensibility

**Key Architectural Differences:**
1. **Component Granularity**: ta4j uses fine-grained composable objects (190+
   indicators, Rule objects, Strategy objects). backtest-engine uses coarse-
   grained functions (compute_indicators batch processes all, conditions
   evaluated in condition_engine)

2. **Data Flow**: ta4j uses lazy evaluation with caching (pull model).
   backtest-engine uses eager evaluation (push model - compute all upfront)

3. **Position Management**: ta4j supports partial fills with FIFO/LIFO/AVG_COST
   matching policies. backtest-engine uses atomic fills (one entry, one exit)

4. **Execution Models**: ta4j has pluggable TradeExecutionModel (next-open,
   current-close, slippage, stop-limit). backtest-engine hardcodes next-open
   with fixed slippage model

5. **Language/Ecosystem**: ta4j is Java (JVM ecosystem, 190+ built-in indicators,
   type safety). backtest-engine is Python (pandas/numpy, 30+ indicators,
   dynamic typing)

SECTION 3: INDICATOR COMPUTATION
================================================================================

ta4j: LAZY EVALUATION WITH CACHING
-----------------------------------
- Indicators implement Indicator<T> generic interface
- getValue(int index) computes on-demand when requested
- CachedIndicator memoizes results to avoid recomputation
- Composable chains: EMA(SMA(close, 20), 10) forms dependency DAG
- Type-safe: Indicator<Num> for numerical, Indicator<Boolean> for conditions
- Pull model: Backtester pulls indicator values bar-by-bar

Example flow (ta4j):
1. Backtest requests EMA value at bar 100
2. EMA checks cache → miss
3. EMA requests SMA value at bar 100
4. SMA checks cache → miss, computes, caches
5. EMA computes from SMA result, caches
6. Next request for bar 100 → cache hit (both levels)

Pros:
+ Memory efficient (compute only requested indices)
+ Cache reuse across nested indicators
+ Deterministic (no accidental future access)

Cons:
- Complexity (cache management, chain traversal)
- Potential stack overflow on deep chains (mitigated with prefill)

backtest-engine: EAGER BATCH COMPUTATION
------------------------------------------
- compute_indicators(df, indicators_list) computes ALL bars upfront
- Uses pandas-ta library (vectorized operations)
- Returns DataFrame with new indicator columns
- trim_warmup_period() removes leading NaN bars
- Push model: All indicators computed before backtesting starts

Example flow (backtest-engine):
1. fetch_ohlcv() returns 1000-bar DataFrame
2. compute_indicators() computes SMA(20), EMA(10), RSI(14) for ALL 1000 bars
3. trim_warmup_period() removes first 20 bars (warmup)
4. run_backtest() iterates over remaining 980 bars with all indicators ready

Pros:
+ Simple implementation (single batch operation)
+ Leverages pandas vectorization (faster for large datasets)
+ No cache management overhead

Cons:
- Memory inefficient (computes ALL bars even if backtest exits early)
- Warmup handling is explicit manual step
- No indicator composition (must pre-compute intermediate indicators)

SECTION 4: POSITION MANAGEMENT
================================================================================

ta4j: PARTIAL FILLS WITH LOT MATCHING
--------------------------------------
TradingRecord tracks:
- TradeFill objects: (index, time, price, amount, fee, side, orderId, correlationId)
- Four matching policies: FIFO, LIFO, AVG_COST, SPECIFIC_ID
- Separate open vs closed positions tracking
- Cost models: transactionCostModel + holdingCostModel

Two interaction patterns:
1. Stream fills: tradingRecord.operate(TradeFill) for live execution
2. Batch trades: Trade.fromFills(List<TradeFill>) to group partials

Use case: Accumulating position over multiple entries
- Enter 100 shares at $50 (fill 1)
- Enter 50 shares at $52 (fill 2)
- Exit 75 shares at $55 (fill 3)
- FIFO: closes 75 of first 100 shares → 25@$50 + 50@$52 remain
- LIFO: closes 50@$52 + 25@$50 → 75@$50 remain
- AVG_COST: cost basis = (100*50 + 50*52) / 150 = $50.67

backtest-engine: ATOMIC FILLS
-------------------------------
PositionState tracks:
- Single entry: entry_price, entry_bar, shares
- Single exit: exit_price, exit_bar
- NO partial fills, NO lot matching
- Trades are complete: one entry → one exit → closed

Use case: One position at a time
- Enter 100 shares at $50
- Exit signal → close ALL 100 shares
- Next entry is a NEW position (no accumulation)

Limitations:
- Cannot model DCA (dollar-cost averaging) into existing position
- Cannot model partial exits (scale out)
- periodic_contribution feature adds cash but doesn't accumulate shares

Design implication:
- "DCA" is misleading name (really "periodic cash injection")
- See BUG DCA-001 in ENGINE_REVIEW_V2_ISSUES.txt

SECTION 5: EXECUTION MODELS
================================================================================

ta4j: PLUGGABLE VIA STRATEGY PATTERN
--------------------------------------
TradeExecutionModel interface with implementations:

1. TradeOnNextOpenModel (default, same as backtest-engine)
   - Entry signal at bar i → fill at bar i+1 open
   - Exit signal at bar i → fill at bar i+1 open

2. TradeOnCurrentCloseModel
   - Entry signal at bar i → fill at bar i close
   - Higher look-ahead bias risk

3. SlippageExecutionModel
   - Applies market impact: buy pays more, sell receives less
   - Configurable slippage % or function

4. StopLimitExecutionModel
   - Intra-bar stop-loss and take-profit triggers
   - Uses bar high/low for realistic fill prices

Injection pattern:
```java
BarSeriesManager manager = new BarSeriesManager(
    series,
    new SlippageExecutionModel(0.001), // 0.1% slippage
    transactionCostModel,
    holdingCostModel
);
```

backtest-engine: HARDCODED NEXT-OPEN
--------------------------------------
Execution timing:
- Entry signal at bar i → pending_entry=True
- Next bar i+1 → fill at open_price
- Exit signal at bar i → pending_exit=True
- Next bar i+1 → fill at open_price

Slippage model (FIXED %):
- is_buy=True: execution_price = price * (1 + slippage_pct/100)
- is_buy=False: execution_price = price * (1 - slippage_pct/100)

Intra-bar stops:
- Stop loss: checks bar_low/bar_high vs stop price
- Take profit: checks bar_low/bar_high vs tp price
- Dynamic stop: reads indicator column value each bar
- Liquidation: checks bar_low/bar_high vs liquidation price

Commission models:
- Fixed: commission_per_trade ($ per entry/exit)
- Percentage: commission_pct (% of notional)

Design issues (from ENGINE_REVIEW_V2_ISSUES.txt):
- CRIT-001: Slippage model unrealistic (fixed % doesn't reflect liquidity)
- DYN-002: Dynamic stop is NOT trailing (reads indicator, doesn't track max)

SECTION 7: RULE/CONDITION EVALUATION
================================================================================

ta4j: COMPOSABLE RULE OBJECTS
-------------------------------
Rule interface:
- isSatisfied(int index, TradingRecord tradingRecord) → boolean
- Fluent composition: rule1.and(rule2).or(rule3).not()
- Stateless vs stateful rules

Example (Java):
```java
Rule entryRule = new CrossedUpIndicatorRule(shortSma, longSma)
    .and(new OverIndicatorRule(rsi, 30))
    .and(new OpenedPositionMinimumBarCountRule(10).negation());

Rule exitRule = new CrossedDownIndicatorRule(shortSma, longSma)
    .or(new UnderIndicatorRule(rsi, 70));

Strategy strategy = new BaseStrategy(entryRule, exitRule);
```

Stateless example: CrossedUpIndicatorRule
- Ignores TradingRecord parameter
- Evaluates purely from indicator values at given index

Stateful example: OpenedPositionMinimumBarCountRule
- Queries TradingRecord.getCurrentPosition()
- Calculates bars since entry
- Prevents exit within first N bars

backtest-engine: JSON-BASED CONDITION GROUPS
----------------------------------------------
ConditionGroup model:
- logic: "AND" | "OR"
- conditions: list of Condition objects

Condition model:
- left_operand_type: "INDICATOR" | "OHLCV" | "SCALAR" | "LOOKBACK"
- left_operand_value: column name or value
- operator: "GT" | "LT" | "EQ" | "CROSSES_ABOVE" | "CROSSES_BELOW" | ...
- right_operand_type/value

Example (JSON):
```json
{
  "logic": "AND",
  "conditions": [
    {
      "left_operand_type": "INDICATOR",
      "left_operand_value": "sma_50",
      "operator": "CROSSES_ABOVE",
      "right_operand_type": "INDICATOR",
      "right_operand_value": "sma_200"
    },
    {
      "left_operand_type": "INDICATOR",
      "left_operand_value": "rsi_14",
      "operator": "GT",
      "right_operand_type": "SCALAR",
      "right_operand_value": "30"
    }
  ]
}
```

Evaluation:
- evaluate_conditions(df, condition_group) → boolean Series
- Always stateless (no access to position state)
- AND/OR composition only (no NOT, XOR)

Limitations:
- No position-aware rules (can't check "bars since entry")
- No programmatic composition (must build JSON)
- No custom rule types (fixed operator set)

SECTION 8: POSITION SIZING
================================================================================

ta4j: CONTEXT-AWARE POSITIONSIZER
-----------------------------------
PositionSizer interface (Java @FunctionalInterface):
```java
Num sizePosition(Context ctx, TradingRecord tradingRecord);
```

Context record contains:
- signalIndex, entryIndex, entryPrice
- strategy, barSeries, tradeType
- tradingRecord (for position-aware sizing)
- transactionCostModel, holdingCostModel

Built-in implementations:
- PositionSizer.fixed(Number n) → constant shares
- PositionSizer.balance() → use all cash
- PositionSizer.kelly(coefficient) → Kelly criterion

Custom example (Java):
```java
PositionSizer customSizer = (ctx, record) -> {
    Num cash = record.getCurrentCash();
    Num price = ctx.entryPrice();
    Num atr = atrIndicator.getValue(ctx.entryIndex());
    Num stopDistance = atr.multipliedBy(2);
    Num riskAmount = cash.multipliedBy(0.02); // 2% risk
    return riskAmount.dividedBy(stopDistance);
};
```

backtest-engine: INLINE SIZING WITH MODES
-------------------------------------------
_calculate_position_size() function with modes:

1. full_capital
   - amount_to_invest = cash
   - shares = cash / price

2. percent_capital
   - amount_to_invest = total_capital * (position_size_value / 100)
   - shares = amount / price

3. fixed_amount
   - amount_to_invest = position_size_value
   - shares = amount / price

4. risk_based
   - risk_amount = total_capital * (position_size_value / 100)
   - stop_distance = |price - stop_price|
   - shares = risk_amount / stop_distance

Design issues (from ENGINE_REVIEW_V2_ISSUES.txt):
- SIZE-001: total_capital uses cash only, not equity
- SIZE-003: Leverage multiplies shares AFTER sizing (breaks risk_based)
- SIZE-005: full_capital doesn't reserve for commission
- SIZE-006: Leverage commission formula wrong in recalculation

SECTION 9: KEY PHILOSOPHICAL DIFFERENCES
================================================================================

1. GRANULARITY
--------------
ta4j: Fine-grained objects
- Each indicator is a class
- Each rule is a class
- Each cost model is a class
→ High composability, high verbosity

backtest-engine: Coarse-grained functions
- compute_indicators() batch processes
- evaluate_conditions() handles all conditions
- run_backtest() does everything
→ Low composability, low verbosity

2. EXTENSIBILITY
----------------
ta4j: Inheritance-based
- Extend AbstractIndicator<T>
- Implement Rule interface
- Implement CostModel interface
→ Requires Java knowledge, strong typing

backtest-engine: Configuration-based
- Add indicator to pandas-ta wrapper
- Add operator to condition_engine
- Modify state_machine for new features
→ Requires Python knowledge, modify core code

3. TESTABILITY
--------------
ta4j: Unit-testable components
- Test indicators in isolation
- Test rules with mock BarSeries
- Test execution models independently

backtest-engine: Integration-heavy testing
- Smoke tests run full end-to-end
- Unit tests mock entire flows
- Harder to isolate components

4. REAL-WORLD ALIGNMENT
-----------------------
ta4j: Partial fills model
- TradeFill granularity matches broker APIs
- FIFO/LIFO matching matches real lot tracking
- Cost models separate transaction vs holding

backtest-engine: Simplified model
- Atomic fills (no partials)
- Single entry/exit per position
- Combined commission model

Both suffer from:
- Unrealistic slippage models (fixed % vs order book depth)
- No market impact modeling
- No liquidity constraints

SECTION 10: BUGS AND DESIGN ISSUES COMPARISON
================================================================================

ta4j KNOWN LIMITATIONS (from research):
- Thread-safety of CachedIndicator unclear (claims refuted)
- No explicit warmup handling (relies on lazy evaluation)
- Ring buffer cache eviction not verified
- Cost model integration math not deeply verified

backtest-engine CRITICAL BUGS (from ENGINE_REVIEW_V2_ISSUES.txt):

CRITICAL (6 issues):
1. DATA-007: Binance uses FUTURES API, not spot (price divergence)
2. SIZE-003: Leverage breaks risk_based sizing
3. DYN-002: Dynamic stop is NOT trailing
4. CT-NEW-009: SHORT counter-trade leverage uses wrong proceeds formula
5. ATTR-001: Attribution uses signal bars vs fill bars (timing mismatch)

HIGH (12 issues):
- Counter-trade inherits leverage
- DCA doesn't add to existing positions
- Market return uses close, fills use open
- NaN skip_col treated as skip
- total_capital uses cash only
- full_capital no commission reserve
- Leverage commission formula wrong
- No validation for negative dynamic TP
- Timezone inconsistency between providers
- Date boundary double-addition

Total: 48 issues (6 critical, 12 high, 16 medium, 14 low)

**Implication**: backtest-engine has significantly more correctness bugs than
ta4j, especially around advanced features (leverage, counter-trades, attribution).
Core functionality (basic long-only backtesting) is sound, but optional features
have serious issues.

SECTION 11: WHEN TO USE WHICH
================================================================================

Use ta4j when:
✓ Building Java/JVM applications
✓ Need strong type safety and compile-time checks
✓ Require partial fills and lot matching (real-world execution model)
✓ Want built-in parameter sweep parallelization
✓ Need real-time trading integration (ConcurrentBarSeries)
✓ Prefer object-oriented composition over functional pipelines

Use backtest-engine when:
✓ Building Python/pandas-based applications
✓ Leveraging pandas ecosystem (data munging, visualization)
✓ Need web API + async task execution (FastAPI + Celery)
✓ Want declarative strategy definition (JSON-based, store in DB)
✓ Building a SaaS platform (multi-tenant, user-defined strategies)
✓ Prototyping is more important than production correctness

================================================================================
SECTION 12: ARCHITECTURAL RECOMMENDATIONS FOR backtest-engine
================================================================================

Based on ta4j's proven patterns, consider these improvements:

1. MAKE EXECUTION MODEL PLUGGABLE
   - Extract fill logic into ExecutionModel interface
   - Support next-open, current-close, slippage variants
   - Allow users to inject custom models
   - Fix slippage model to be market-impact-aware (order book depth)

2. ADD INDICATOR COMPOSITION
   - Allow indicators to reference other indicators as inputs
   - Implement lazy evaluation for memory efficiency
   - Add warmup tracking per indicator

3. SUPPORT PARTIAL FILLS
   - Introduce Fill dataclass (time, price, shares, commission, id)
   - Track Position as list of fills
   - Implement FIFO/LIFO/AVG_COST matching
   - Fix DCA to actually accumulate shares

4. SEPARATE COST MODELS
   - Split commission into TransactionCostModel
   - Add HoldingCostModel (margin interest, borrow fees)
   - Make models pluggable (different brokers have different fee schedules)

5. ADD PARAMETER SWEEP FRAMEWORK
   - Native support for grid search / random search
   - Parallel execution via multiprocessing (not just Celery)
   - Built-in ranking with multi-objective optimization

6. IMPROVE POSITION SIZING
   - Add PositionSizer interface with context
   - Fix SIZE-001: use equity, not cash
   - Fix SIZE-003: leverage-aware sizing
   - Add Kelly criterion, volatility-based sizing

7. FIX CRITICAL BUGS
   - DATA-007: Add api_type='spot'|'futures' parameter to Binance provider
   - DYN-002: Implement actual trailing stop logic
   - ATTR-001: Fix bar index mismatch (use fill bars, not signal bars)
   - SIZE-003: Make _calculate_position_size leverage-aware

8. ADD RULE COMPOSITION
   - Allow programmatic rule building (not just JSON)
   - Support .and(), .or(), .not() composition
   - Add position-aware rules (bars_since_entry, unrealized_pnl, etc.)

9. IMPROVE TYPE SAFETY
   - Add Pydantic models for all schemas
   - Add mypy type hints throughout
   - Validate indicator parameters at strategy creation time

10. ENABLE REAL-TIME TRADING
    - Add StreamingDataFrame or similar for live bar ingestion
    - Separate backtest engine from live execution logic
    - Support incremental indicator updates

================================================================================
CONCLUSION
================================================================================

**ta4j strengths:**
- Mature architecture (10+ years in production)
- Clean separation of concerns
- Pluggable execution models
- Partial fills support
- Built-in parallelization

**backtest-engine strengths:**
- Modern web stack (FastAPI + React)
- Declarative strategy definition
- User-friendly API
- Pandas/numpy ecosystem integration

**Key takeaway:**
backtest-engine's architecture is optimized for SIMPLICITY (single-user, batch
processing, declarative strategies) while ta4j's architecture is optimized for
FLEXIBILITY (multi-user patterns, real-time, programmatic strategies).

For backtest-engine to reach production-grade quality:
1. Fix 48 documented bugs (prioritize 6 critical, 12 high)
2. Adopt ta4j's pluggable execution model pattern
3. Support partial fills for realistic position management
4. Add parameter sweep framework
5. Improve type safety and validation

The gap is NOT insurmountable, but it requires systematic refactoring guided
by ta4j's proven patterns.
